## 5. 추가 기술 후보 3가지 — 있으면 유리한가, 손해인 경우는

| 후보 | 유리한 경우 | 손해가 나는 경우 | 판단 |
|---|---|---|---|
| **KTX2**(GPU 압축 텍스처, Basis) | 텍스처가 많고 큰 장면. WebP/JPG는 GPU에서 풀리면 2048² 한 장이 약 16 MB(밉맵 포함 21 MB)인데 KTX2는 약 3–6 MB라 **GPU 메모리 4–8배 절약**, 업로드 시 디코드가 없어 **스크롤 중 끊김(업로드 멈춤) 감소**. REF-002 원본이 사용 | ① **품질 손실**: ETC1S는 블록 무늬 — 부드러운 그라데이션인 **조명 이미지·sqrt 인코딩 데이터에 특히 나쁨**(UASTC는 괜찮지만 다운로드가 WebP의 2–4배). ② 트랜스코더 wasm 약 0.5 MB + 로더 설정. ③ 빌드 도구 추가(`toktx` 또는 npm `ktx2-encoder` 0.6.0), UASTC 인코딩이 느림. ④ 텍스처가 몇 장뿐이면 이득 거의 없음 | 전시 PC VRAM 예산(P2)을 넘거나 **스크롤 중 업로드 멈춤이 측정될 때** 도입. 도입해도 조명 이미지는 UASTC 또는 WebP 유지. 이번 다락방(텍스처 약 40장)은 도입 검토 대상 |
| **pmndrs `postprocessing`** | 효과 5개 이상을 **한 패스로 병합**해 전체 화면 패스 수 감소(성능), 고품질 효과 기본 제공(SMAA, N8AO, 밉맵 블룸, DOF, LUT, GodRays) | ① three 버전 결합: 현재 버전은 **three `>=0.168 <0.187`**만 지원 — three를 올리면 이 라이브러리 업데이트를 기다려야 함 `[런타임]` ② 기존 `EffectComposer` 코드와 섞어 쓸 수 없어 재작성 ③ 번들 증가 ④ three의 WebGPU/TSL 후처리로 가면 다시 이전 ⑤ 이번처럼 **장면 특화 효과**(깊이 지도 레이마칭)는 어차피 직접 작성 | 지금 규모(효과 5–6개, 1개는 직접 작성)에서는 **불필요**. 효과가 늘고 GPU 프로파일에서 패스 수가 병목으로 나오면 도입 |
| **Theatre.js** | 카메라 경로·타이밍을 **타임라인 편집기**로 사람이 직접 조정 → 아트 디렉션 반복을 사용자가 코드 없이 | ① **2024-05의 0.7.2 이후 릴리스가 없음**(2년 넘게 정체) `[런타임]` — 장기 유지보수 위험 ② 편집기(studio)는 개발용이라 배포 번들에서 빼는 설정 필요 ③ 스크롤 연결은 직접 구현 ④ 키프레임이 3–5개면 **코드 상수가 더 단순하고 AI가 수치로 고치기 쉬움**(이번 방식) ⑤ JSON 상태와 코드 이중 관리 | **보류**. 여러 장면(5개 이상)의 카메라 안무를 사용자가 직접 만지고 싶을 때만. 대안: 간단한 자체 키프레임 편집 패널(개발 전용)을 만드는 편이 위험이 적음 |

요약: 세 가지 모두 "있으면 무조건 유리"한 것은 아니다. **문제가 측정된 뒤에 넣는 도구**다 — KTX2는 GPU 메모리·업로드 멈춤, postprocessing은 패스 수 병목, Theatre.js는 사용자가 직접 안무를 편집하고 싶을 때.
