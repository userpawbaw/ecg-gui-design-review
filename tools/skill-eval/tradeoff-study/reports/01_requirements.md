# 01. 요구사항 명세 — 최적화 · 튜닝 스킬 재검증 (2026-11-11)

기존 스킬(`skill-snapshot-v1/`, D-171)은 초안으로 취급한다. 이 문서는 원래 요청을 다시 읽고 검증 가능한 요구사항으로 바꾼 것이다.

## 1. 원래 요청 (사용자 원문, 2026-11-11)

> 제약사항과 현재의 환경에서 굳이 필요하지 않은 최적화 여지 부분을 같이 분석한 후, 선택 가능한 최적화 방식 간의 트레이드 오프를 분석해서 각 방식 중 우리 환경에서 최선의 방식이나 트릭을 찾는 (트레이드 오프의 손해가 제약사항+최적화 여지 환경에서 중요하지 않아 품질-성능 _품질과 성능 모두 각기 여러 기준이 있을 수 있겠지만_ 이 모두 최선인) 이 과정은 어떤 작업에서나 필수적일 것 같아. … 구조적인 설계 환경 분석+필요하다면 추가 정보를 위한 질문을 진행한 후 자동으로 최선의 방식을 탐색하며 최종적으론 그 분석 및 탐색 과정, 결과 제안을 포함한 보고를 매번 규칙적으로 하도록 만들고 싶어.

## 2. 명료화

| 원래 표현 | 기술적 요구사항 |
|---|---|
| 제약사항 | 깨면 안 되는 조건(정확성 · 데이터 계약 · 사용자 확정 사항 · 대상 환경)과 예산(시간 · 메모리 · 작업량)을 구분해 적는다 |
| 굳이 필요하지 않은 최적화 여지 | 품질 · 정밀도 · 반응성을 낮춰도 사용자가 받는 결과가 달라지지 않는 범위("여유"). 주장이 아니라 근거(측정 · 사용자 발화 · 코드)가 있어야 한다 |
| 최선의 방식이나 트릭 | 하드 제약을 모두 지키고, 손해가 여유 안에만 떨어지며, 그런 후보 중 이득이 가장 큰 것. 그런 후보가 없으면 "진짜 트레이드오프"로 사용자에게 넘긴다 |
| 품질과 성능 각기 여러 기준 | 기준을 한 점수로 합치지 않는다. 기준별 문턱값과 측정 방법을 둔다 |
| 구조적인 환경 분석 | 어디가 실제로 느린지/비싼지 **진단**(측정 · 프로파일)을 포함한다 — 원래 요청에는 암묵적이었고 기존 스킬에는 빠져 있다 |
| 필요하다면 질문 | 답이 선택을 바꾸는 질문만. 나머지는 가정으로 밝히고 진행 |
| 자동으로 탐색 | AI가 스스로 조사 · 후보 생성 · 실험 · 측정을 한다. 사용자가 부르지 않아도 발동 |
| 매번 규칙적으로 보고 | 일정한 뼈대의 보고. 단, 분량은 과제 크기에 비례 |

## 3. 스킬 정의

- **목적**: "어떻게 만들까/어떻게 빠르게 할까"를 정해야 할 때, 이 상황에서 손해 없는(또는 손해가 가장 작은) 방식을 근거와 함께 찾아 적용 · 검증하게 한다.
- **적용 범위**: 소프트웨어의 구현 방식 선택, 성능 · 비용 · 품질 튜닝(렌더링, 코드, 데이터 처리, 구조). 창작 방향 결정, 단순 버그 수정, 이미 확정된 방식의 실행은 범위 밖.
- **입력**: 사용자 요청, 코드 · 실행 환경 접근, 사용자가 말한 필요 수준, (있으면) 프로젝트의 과거 기록.
- **출력**: ① 결정과 근거(무엇을 얻고 무엇을 잃는지, 어디서 뒤집히는지) ② 권한이 있으면 적용된 변경 ③ 전후 측정 ④ 사용자에게 남긴 결정 · 미검증 항목.
- **실행 환경**: Claude Code 계열 에이전트(파일 · 셸 도구). 대화형이 아닐 수도 있다(질문 도구가 없으면 질문을 답변에 적는다).
- **이식성**: 핵심 지침은 특정 프로젝트 없이 동작해야 한다. 프로젝트 기록(F/D/O/R 등) 연동은 선택 부분으로 분리한다 — 새 요구.

## 4. 성공 기준 (평가 항목으로 연결)

1. **진단**: 실제 병목 · 원인을 맞힌다. 사용자가 틀린 원인을 말해도 확인 없이 따르지 않는다.
2. **해법 적합성**: 하드 제약을 어기지 않는다. 더 단순한 해법이 있으면 그것을 고른다.
3. **달성 성능**: 실행 가능한 과제에서 측정된 개선이 기준 해법 수준에 이른다.
4. **검증**: 바꾸기 전 기준값을 재고, 같은 조건으로 다시 재며, 정확성 검사를 통과시킨다. 못 잰 것은 못 쟀다고 쓴다.
5. **사용자 개입**: 물어야 할 때(목표 불명, 실손이 있는 선택, 되돌리기 어려운 변경) 묻고, 물을 필요 없을 때 묻지 않는다.
6. **비례성**: 작은 과제에 큰 절차를 쓰지 않는다. "최적화하지 않는다"가 답일 수 있다.
7. **보고**: 권장 · 얻는 것 · 잃는 것 · 뒤집히는 조건 · 미검증이 빠지지 않는다.

## 5. 누락 · 수정 · 제거

| 구분 | 내용 | 이유 |
|---|---|---|
| **누락(추가)** | 진단 단계: 후보를 만들기 전에 병목을 측정으로 확인 | 틀린 곳을 최적화하면 나머지가 다 맞아도 이득이 없다(암달의 법칙). 기존 스킬은 여유 지도에서 바로 레버로 간다 |
| **누락(추가)** | 적용 → 측정 → 해석 → 다시/그만의 순환과 종료 기준 | 기존 스킬은 보고에서 끝난다. 목표 도달 · 한계 효용 · 사용자 판단 필요 시 멈춰야 한다 |
| **누락(추가)** | 바꾸기 전 기준값과 정확성 보호 장치(테스트 · 출력 비교) | 최적화가 결과를 바꾸는 사고를 막는다 |
| **누락(추가)** | "하지 않는다"도 정답 후보 | 이미 충분하면 손대지 않는 것이 최선 |
| **누락(추가)** | 사용자 피드백 평가(무조건 수용 · 무시 금지), 승인 권한 분리 | 지침 5절 |
| **수정** | "모두 최선" → "실손 없음 우선, 없으면 사용자에게 진짜 트레이드오프 제시" | 여러 기준이 동시에 최선인 해는 흔히 없다(파레토). 원래 문장도 "손해가 중요하지 않아"라는 조건을 달았다 |
| **수정** | "매번 보고" → 규모 비례 보고 | 한 줄 수정에 열 칸 보고는 비용만 든다 |
| **제거 검토** | 10칸 고정 양식, 가중치 · 파레토 용어 강제, 12개 레버 전수 대입 | 실행 품질에 기여하는지 검증된 바 없다. 평가에서 효과가 없으면 줄이거나 참조 자료로 내린다 |
| **범위 밖** | 창작 방향(Alpha/Beta), 단순 구현 실행 | 다른 워크플로가 담당 |

## 6. 상충과 검증 한계

- **자동 발동 vs 비용**: 매번 돌리면 작은 작업이 느려진다 → 규모 판정과 "생략" 조건을 스킬의 일부로 평가한다.
- **자율 vs 승인**: AI가 측정 · 실험은 스스로 하되, 실손이 있는 선택과 요구 축소는 사용자 몫.
- **검증하기 어려운 것**: 지각 품질("안 보인다"), 대상 장비 성능, 장기 유지 비용. 스킬은 이것을 "미검증"으로 분리해 보고해야 하고, 평가도 이 항목은 채점자 판단으로만 한다.
- **평가 자체의 한계**: 사례 수가 적다(개발 5 · 미공개 4 안팎). 통계적 유의성은 주장하지 않는다.

## 7. 역할 분담

| AI가 자율 수행 | 사용자 판단 필요 |
|---|---|
| 코드 · 기록 조사, 프로파일 · 측정, 후보 생성, 되돌릴 수 있는 실험, 전후 비교, 보고 | 목표 수준과 "충분함"의 기준(없을 때), 실손이 있는 선택, 요구 자체의 축소, 되돌리기 어렵거나 비싼 변경, 지각 품질의 최종 확인, 최종 승인 |

핵심 목적은 바꾸지 않았다. 바꾼 것은 실행 방식(진단 · 순환 · 종료 · 비례)이다.
