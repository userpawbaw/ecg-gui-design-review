## 배경

CASE-005에서 creative 경로를 Alpha(구현 인지)/Beta(이미지 우선)로 바꾼 뒤에도, 결과물이 우수 레퍼런스의 연출 수준에 미치지 못한다는 문제가 남았다. 이 CASE는 그 원인을 "발상"이 아닌 "제작 정보와 재료의 부재"로 재정의하고, 레퍼런스 분석을 재현용 기록으로 강제하는 규칙을 만든 과정이다.

## 논의 흐름

### 1. 사용자가 문제를 "백엔드적 체계"로 재정의했다

> "wow 포인트를 제대로 살리지 못하는 감이 있더라고. 때문에 유사 효과를 만드는 데 필요한 에셋이나 사전 구축할 자료 … 필요 기술 스택 확인 등 좀 더 백엔드적으로 체계를 더 구축할 필요가 있다고 느꼈어."

AI는 원인을 여섯 가지 빈칸(Canvas 2D 상한, 에셋 계층 없음, timeline 엔진 없음, 정지 이미지 분석, 전시 입력 번안 없음, 연출 QA 없음)으로 진단하고, three.js + GSAP + Lenis spike로 메커니즘을 확인했다(F-010).

### 2. 녹화가 AI의 첫 해석을 뒤집었다

AI는 캡처 1장과 사이트 태그로 "지구 회전"을 크게 구현했다. 사용자가 녹화를 제공하자, 실제 wow는 역광과 지구 → 선 → 카드 모서리로 이어지는 match cut이라는 것이 드러났다(F-011).

### 3. 사용자가 관찰을 날카롭게 질문했다

> "스크롤 할 때의 빠른 속도 회전과 멈췄을 때의 느린 속도 회전 간의 전환이 부드러워. 이건 어떻게 구현한 걸까?"

> "38~39초에 스크롤 잠시 멈추는 걸 보면 좀 끊기는 것처럼 보이지 않아?"

AI는 녹화를 60 fps로 풀어 상관·감쇠를 측정했고, 사용자는 촬영 규칙을 제안했다("먼저 스크롤을 멈추고 정지 상태의 효과를 본 뒤 규칙적으로 스크롤"). 순서는 고정하고 시간은 대략으로 하는 D-017이 이렇게 정해졌다.

### 4. 소스 확인이 녹화 기반 추정을 다시 정정했다

네트워크 허용 뒤 소스를 읽으니, "속도 비례 회전"은 위치 연동 + `scrub: 1`이었고, 부드러운 감속은 원통 갤러리의 wheel 충격 + 감쇠였다(F-012). 같은 관찰값이 다른 메커니즘에서 나올 수 있다는 것이 확인되었다.

### 5. 사용자가 기록의 목적을 못박았다

> "기록 없이 분석만 진행하면 컨텍스트 오염 가능성이 있으니, 기록 규칙이 확정되면 첫번째 사이트 분석을 기록 규칙에 맞게 작성해."

> "이 기록 규칙은, 나중에 이 레퍼런스 수준의 고품질 UI/UX 설계 시스템에서 해당 레퍼런스들의 특징적인 효과를 구현하기 위해 필요한 정보들이 담겨 있도록 강제하는 용도야."

AI는 이를 "문서만 읽고 사이트를 다시 열지 않아도 재현 계획을 세울 수 있는가"라는 합격 기준으로 옮기고, 효과 카드 15개 필드와 자동 검사를 설계했다(D-018).

### 6. 사용자가 "한 장"의 검증을 "구간"의 검증으로 바꿨다 (2026-09-26)

AI는 REF-003 경로를 캡처 1–2장과 진행률 숫자로 확인하고 재현 완료로 보고했다. 사용자는 결과를 보고 원인까지 짚었다.

> "표시지점 뒤, 즉 위치 표시기가 이동한 곡선을 이미 지난 경로라는 것을 알 수 있게 다른 색으로 확실하게 표시해줬는데, 우리 구현에서는 그 부분의 디테일이 부족하네. … 아마도 여러 장을 확인하지 않아서 그런 느낌. 한 대여섯장 이상은 확인해봐야 할 것 같은데?"

AI는 처음에 색 대비 문제 하나로 보았으나, 12장 대조에서 결함이 세 개(대비, 구간 중간의 표시기 이탈, 수정 후 나타난 dash 분할)였다(F-017). 같은 턴에 사용자는 다락방 결과를 보고 "빛 효과 말고도 3d 작업시 셰이더나 후처리를 항상 검토하도록" 요청했다. 두 요청은 "빠진 층을 체계적으로 찾는 검증"이라는 같은 규칙으로 묶였다(D-019, 체크리스트 §12, 21번 §8).

사용자는 외부 UI 컴포넌트가 "직접 만드는 경우보다 나을 지 아닐 지 확실히 알고 싶"다고 했다. AI는 의견 대신 같은 데이터로 두 변형을 만들어 같은 12장 규칙으로 판정했고, 컴포넌트는 wow 포인트(정지 소나)에서 FAIL, 번들 2배 이상이었다 — 외부 컴포넌트는 기법 공급원으로 둔다(D-021). 에셋 조달처도 같은 방식으로 "접근·라이선스·자동 받기"를 실제로 시험한 뒤 순서에 넣었다(D-020).

### 7. 사용자가 제작 경로 자체를 넓혔다 — AI 영상, 계정 조달처, 컴포넌트 검토 (2026-09-26)

사용자는 실시간 3D·Blender 외의 경로를 제안했다.

> "고정적인 스크롤 방식에서는 어쩌면 AI로 해당 레퍼런스를 참조하게 하여 우리가 원하는 구도로 동영상을 제작시킨 후 그걸 부드럽게 스크롤 에니메이션으로 적용하는 방식을 생각해볼 수도 있고. … 이게 더 쌀 수도 있지? 이 프로세스를 완성도있는 별도 시스템으로 구축해서 테스트해볼 테니, 검토해서 보완할 점이나 새로 추가할 점, 수정할 점을 찾아봐줘."

AI는 발상을 유지하되 네 가지를 바꿨다: 레퍼런스를 생성 입력으로 넣지 말고 원칙은 글·구도는 우리 키프레임으로(수정), "가감속"을 스크롤 관성과 영상 자체 속도의 두 층으로 나눠 광류 기반 속도 보정을 추가(보완), 평면 영상으로는 REF-002의 "고개 돌림"이 안 된다는 기대치 조정, 입고 QA·3회 상한·적합성 판정(추가). 대역 클립과 결함 주입 클립으로 도구를 먼저 증명했다(D-023). 설계 검토 중 AI가 스스로 디코딩 메모리 문제(≈ 885 MB)를 찾아 고쳤고(F-018), 12장 확인이 첫 장의 로딩 문구 잔상을 잡았다 — D-019 규칙이 새 영역에서도 작동했다.

사용자는 또 다른 AI와 조사한 UI 컴포넌트 목록을 가져오며 "실제 접근 가능한지는 검토해줘야 해"라고 했다. 확인 결과 대부분 접근되지만, Origin UI는 coss.com/ui로 옮기며 **AGPL-3.0**이 되었고, 영감 사이트 다수는 403·로그인이었다. 사용자의 제안대로 "예측 → 실제 비교" 단계(C1–C4)를 만들고, 목록은 미사용 상태로 기록했다(D-024). 에셋은 계정을 만들겠다는 사용자 결정에 맞춰, 후보가 있을 때만 로그인을 요청하는 흐름을 만들었다(D-022).

### 8. 사용자의 반박이 AI의 "한계" 판단을 시험대로 옮겼다 (2026-09-26)

AI는 7절 보고에서 "REF-002의 고개 돌림은 실시간 3D라서 가능했고, 평면 영상으로는 한계"라고 말했다. 사용자는 이를 되물었다.

> "기대치 조정 부분은 한계가 어딘지를 얘기한 거잖아? 고개를 돌리면 새로운 부분이 보이는 느낌을 주는 거는 영상을 그렇게 만들어 달라고 하면 가능하지?"

AI는 말로 답하지 않고 우리 다락방 장면에서 진짜 회전·이동 렌더와 흉내 방식을 픽셀로 비교했다. 측정 도중 AI 자신의 부호·배율 실수와 렌더 잡음이 결과를 뒤집었다가 바로잡혔고, 최종적으로 **REF-002형 제자리 회전은 여백 이동으로 거의 정확히 된다**는 결과가 나왔다 — 첫 판 판단이 틀렸다(F-019). 동시에 사용자가 떠올린 "시점을 바꾼 영상"을 마우스로 섞는 방식은 잔상이 생긴다는 것도 드러났다.

사용자는 AI 브리프의 "레퍼런스를 입력하지 말 것"이 학습 단계에서만 맞는 규칙이라고 지적했다.

> "이건 정답지라서 그런 거고 … 이 경험들을 바탕으로 다른 프로젝트에 적용시키려고 할 때엔 영상으로 제공해도 무방하다는거지."

AI는 이를 단계별 입력 정책으로 옮기면서, 권리 위험을 줄이는 대안으로 "레퍼런스 대신 **우리 재현 결과**를 참고 입력으로"를 더했다(D-025). 정지 문제에 대한 사용자의 두 방식은 둘 다 구현해 시험했고, 쓰임새가 갈렸다(F-020, D-026). 사용자의 "접속만 된다는 건 아예 못 받는다는 뜻이냐"는 질문은 AI 표현의 모호함을 드러냈다 — 실제로는 다섯 곳 모두 받을 수 있었고, 받는 코드를 안 만들었을 뿐이었다.

### 9. 보류했던 결정이 실험의 누적으로 닫혔다 (2026-09-26)

2026-09-25 사용자는 P1(파이프라인 채택)을 "레퍼런스 2~3개를 더 분석한 뒤 결정"으로 미뤘다 `[대화]`. 그 사이 레퍼런스 4개 분석, 재현 spike, 다락방, 12장 규칙, 컴포넌트 A/B, AI 영상 경로를 거치며 원 제안 7계층 중 5개가 이미 쓰이고 있었다. 사용자는 AI 영상 파이프라인을 확정한 뒤 이렇게 말했다.

> "AI 영상 파이프라인 확정하고 P1, P5, P6 결정으로 넘어가자."

AI는 각 안건의 현재 구현 상태와 증거(재현된 결함 수, 번들 크기, 톤 수렴 수치)를 요약하고 선택지 세 개씩을 권장안과 함께 제시했다. 사용자는 세 안건 모두 권장안을 골랐다: HIGH·MEDIUM 전체 채택, vanilla 엔진 + React 마운트, 충실도 게이트 전 항목·수정 3회. 결정이 빠르게 닫힌 이유는 권장의 근거가 대부분 **이미 측정된 결과**였기 때문이다 — 보류 기간이 실험 기간으로 쓰였다.

### 10. 사용자가 기록 자체를 감사하게 했다 (2026-09-26)

결정을 마친 직후 사용자는 재설계로 넘어가기 전에 기록을 먼저 검증하게 했다.

> "기록 규약에 맞게 설계 과정 중 논의내용도 문서화되었는지, 각 결정들이 decision 문서에 잘 담겼는지, 이번 파이프라인 문서가 현재 대화 내용을 모두 확인하고 적절히 요약한게 맞는지 검증해줘."

AI는 압축 요약이 아니라 세션 기록 원문의 사용자 발언 19건을 저장소 기록과 하나씩 대조했다(`handoffs/RECORD_AUDIT_2026-09-26.md`). 대화·handoff에는 있었지만 D로 올라가지 않은 결정 3건(P3 외부 우선, NC 라이선스·등록부, 조명 C 모드), 사고 2건(numpy 충돌, 로컬 실행 실패), AI 교훈 2건(한계 판단 정정, 다른 AI 목록 검증), 소통 선호 1건(한국어 중간 메시지)이 빠져 있었다. 같은 메시지에서 사용자는 로컬 실행이 0 %에서 멈춘다고 알렸다 — AI의 모든 시험이 원본이 있는 자기 컨테이너에서만 돌았다는 것이 드러났다(O-003). R-010("기록이 있다는 것과 중요한 논의가 빠짐없이 기록된다는 것은 다르다")이 이번에도 재현됐다.

### 11. Alpha/Beta 결과의 부족함을 제작 순서의 문제로 다시 정의했다 (2026-09-27)

사용자는 이미지 Beta 시안이 만족스럽지 않았던 원인을 “구체적 화면 설계 없이 임의로 사진을 만들라”는 입력 방식에서 찾고, 레퍼런스 mining/Creative Director 이후 **원본 wow를 여러 번 실제 재현해 기술 스택과 세부 시행착오를 축적 → ECG에 결합할 아이디어를 함께 발상 → 그다음 구체 시안**의 순서를 제안했다 `[대화]`. 다른 AI가 이를 12단계로 정리하면서 REF-003의 12장 자체 검증을 필수 Quality Gate로 올렸다. 이는 사용자가 이 대화에 제공한 제안문이며 그 AI의 이전 대화 전문을 직접 검증한 것은 아니다.

사용자는 별도 검토 메뉴얼을 제공해 “전체 구조 → 각 Phase → Phase 간 연결 → 실행/검증 → 누락 → 3분류” 감사를 요구했다. 특히 상세 서술의 Phase 번호와 압축 목록이 어긋나는 문제까지 잡으라고 했다 `[대화]`. 이번 AI는 `21/25/11`과 실제 REF-003 기록을 확인해, 이미 구현된 다중 프레임 규칙과 **아직 빠진 라우팅·결함 상태·제품 통합**을 구분했다 `[코드]` `[추론]`. 사용자의 “진행하자” 이후 D-038에서 초기 Alpha/Beta 유지, 재현 우선, 모든 작업 의무화의 세 선택지를 비교해 두 번째를 채택하고 `26`을 작성했다 `[대화]` `[코드]`.

또한 공식화 중 원격 최신 R1 Alpha 초안의 F-025와, 작업 중 새로 올라온 D-037 Beta 도구 비교·S01–S07 프롬프트를 확인했다. D1의 잡음별 장면은 서로 다른 기록이므로 “같은 ECG”라는 주장은 동일 합성 기록 D0 S038의 조건 비교에서만 유효하다. 새 Phase 7/11의 자료 의미 게이트에 이 실패 가능성을 넣었다. 기존 R1 packet/Alpha와 사용자 승인으로 진행 중인 독립 Beta 시험은 보존하고, 새 효과의 재현 증거 gap만 따로 평가한다. D-037의 Beta 이미지 PASS는 reference parity가 아니다.

이 변경의 한계: 새 `26` 문서와 라우팅·기록 검사는 **방법론 구현**이다. 모든 EFX의 parity 통과, R1 새 시안, 실제 전시 PC QA를 이번 문서 변경만으로 증명하지 않는다. REF-003 소급 적용과 신규 wow 한 건의 전 과정 시험으로 운영 효과를 다시 평가한다.

## 사용자가 기여한 것

- 12단계 전체에 동일한 검토 틀을 적용하는 메뉴얼을 제공하고 번호·명칭의 미세 불일치까지 감사하도록 요구; 검토 이후 공식화 진행 지시.

## 재사용 가능한 AI 사용 패턴

1. **관찰 → 판별 실험 → 소스 확인의 3단 검증.** 녹화의 상관계수는 메커니즘을 확정하지 못한다. 되돌리기·정지·단발 입력으로 판별하고, 가능하면 소스로 확인한다.
2. **자기 정정을 기록으로 남긴다.** 틀린 추정을 지우지 않고 "추정 → 실제"로 남기면, 다음 분석에서 같은 오판을 막는 규칙이 된다.
3. **분석의 합격 기준을 "재현 가능성"으로 둔다.** 감상이 아니라 숫자·재료·수용 기준이 남았는지를 기계로 검사한다.
4. **컨텍스트 압축 전에 커밋한다.** 긴 분석은 대화가 아니라 저장소에 남아야 다음 세션이 이어받는다.
5. **"나을까?"라는 질문은 같은 데이터·같은 판정 기준의 A/B로 답한다.** 의견보다 12장 대조와 번들 측정이 결론을 빨리 낸다.
6. **AI가 말한 "한계"는 가설로 다루고 측정으로 확인한다.** 이번에는 AI의 한계 판단이 틀렸다(F-019). 사용자의 반박이 측정의 계기였다.
7. **이미 실행한 방법과 아직 라우팅되지 않은 방법을 구분한다.** 6/12장 규칙이 있다고 전체 workflow가 그 순서로 작동하는 것은 아니다. entrypoint, 완료 상태, 기각안, handoff까지 연결해야 후속 AI가 재현을 먼저 수행한다(D-038).
