# J-005. 파형 효과의 연산량 — 실험실 방식 그대로에서 링 스트립 + 선단 창까지

## 출발점

실시간 측정 탭은 D-157에서 원본 live.html 그리기(일반 격자 · 세로 스윕 선)를 옮겨 왔다. 사용자 `[대화]`: "실시간 파형 탭의 파형 표시 방식이 실험실 탭의 파형 표시 개선 노하우가 충분히 적용되지 않은 이전 방식처럼 보임 … 연산량 문제가 있어 측정이 필요". 실험실 효과(D-073)는 매 프레임 전체 경로를 다시 긋고 번짐 3단을 다시 만든다.

## 흐름 한눈에

```
T1 실험실 방식 그대로(기준선) ──(4계열에서 29 fps, 중첩 16 fps)──▶ T2 링 스트립 1차(표본 한 번만 긋기)
   ──(CPU 거의 같음: 비용은 화소 채우기)──▶ T3 선단 창만 층 처리 + 번짐 미리 합치기 ──(dpr 2에서 17 fps)──▶
   T4 창 축소 · 빈칸 미리 비우기 · 번짐 층 ½ · 자동 낮춤 ──▶ T5 사용자: 두 탭 모두 최적화 버전 ── 끝
```

## T1. 실험실 방식 그대로 실시간 탭에

| | |
|---|---|
| 날짜 | 2026-11-08 |
| 종류 | 시도 |
| 계기 | 위 사용자 지시. 최적화 효과를 재려면 같은 효과의 기준선이 있어야 한다 |
| 가설 | 실험실과 같은 코드(`labFx.ts`)를 계열마다 돌리면 모양은 같고 비용만 늘어난다 |
| 판정 | 기각 |
| 다음 | T2 |
| 기록 | D-161, `verification/wave-fx-20261108/README.md`(`wave=naive` 행) |

### 한 것
측정 전용 `?wave=naive`로 계열 4개를 매 프레임 전체 경로 · 64단 그라데이션 · 번짐 3단으로 그렸다.

### 결과
프레임당 CPU가 이전 그리기의 1.8 ~ 3.5배, 초당 그리기 29회(중첩 16회) `[런타임]`.

### 왜 다음으로
계열이 늘면 비용이 그대로 곱해진다. 표본 x가 고정이라는 점(스윕)을 써서 다시 긋지 않는 방법을 찾았다.

## T2. 링 스트립 1차 — 표본은 도착할 때 한 번만

| | |
|---|---|
| 날짜 | 2026-11-08 |
| 종류 | 시도 |
| 계기 | T1의 비용이 매 프레임 전체 경로 재래스터라고 보았다 |
| 가설 | 화면 폭 링 캔버스에 새 표본만 긋고, 잔광 · 사라짐은 미리 구운 램프, 빛점은 스프라이트로 바꾸면 크게 준다 |
| 판정 | 기각 |
| 다음 | T3 |
| 기록 | D-161 「검토한 선택지」 2 |

### 한 것
`waveStrip.ts` 1차: 행마다 층 하나에 번짐 3장 확대 · 램프 4번 · 링 붙이기를 하고 화면에 합성했다.

### 결과
실험실 CPU 63 % → 67 %, 거의 같음 `[런타임]`. 프레임마다 행 크기 화소를 약 14번 채웠다.

### 왜 다음으로
비용의 주인은 꼭짓점 수가 아니라 화소 채우기였다. 채우는 면적을 줄여야 했다.

## T4. 창 축소 · 빈칸 미리 비우기 · 번짐 층 ½ 해상도 · 자동 낮춤

| | |
|---|---|
| 날짜 | 2026-11-08 |
| 종류 | 시도 |
| 계기 | T3의 dpr 2 결과. 단계별 계측에서 합성(`compose`)이 프레임당 34.6 ms로 화소 수에 비례 |
| 가설 | 흰빛 창은 0.6 s(3τ)면 충분하고, 빈칸은 링에서 지워 두면 램프가 필요 없다. 번짐은 흐린 빛이라 CSS ½ 해상도면 된다. 그래도 느리면 실험실처럼 번짐 단계를 자동으로 낮춘다 |
| 판정 | 채택 |

### 한 것
`clearAhead`, 창 0.6 s, 번짐 층 ½, 실시간 정적 층을 CSS 배경으로, 26 ms 넘게 이어지면 번짐 2 → 1 → 0.

### 결과

### 왜 다음으로

## 여정에서 얻은 것

- 캔버스 2D 효과의 비용은 경로가 아니라 채우는 화소 면적이 정한다. 최적화 전에 단계별로 재고, 면적을 줄이는 쪽부터 본다.
- 측정 회차마다 기계 부하가 달라 절대값이 흔들린다. 단계 비교는 같은 회차 안의 비율로 한다.
