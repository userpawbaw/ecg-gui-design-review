# CASE-007. 시행착오를 다음 작업의 출발점으로 — 경험 플레이북(권장 카드 + 여정)이 생긴 과정

관련 기록: D-056, D-057, R-023, R-022, R-020, R-010, R-007, O-007, O-009. 산출물: `docs/playbook/`, `scripts/check-playbook.cjs`.

## 배경

R1 도입부·Story의 사람 모델은 열흘 동안 열다섯 번 방향을 바꿨다(playbook J-001).
- 처음 문제는 플라스틱 마네킹(불쾌한 골짜기)이었다.
- 그 뒤 고리 몸, 달걀 머리, 젖빛 면, 원본 메시 재선택, 손으로 만든 리그, Rigify, 검증기, 리타깃, IK를 거쳤다.
- 마지막으로 사용자가 직접 올린 Mixamo 자동 리깅이 가장 좋았다(D-056).

이 과정의 사실은 F/D/O/R과 `verification/`에 흩어져 있었다. 그러나 다음 두 질문에는 어느 문서도 바로 답하지 않았다.
- "다음에 사람을 리깅하려면 무엇부터 하나?"
- "왜 직접 만들면 안 되나?"

D-056에 해당하는 결정은 D 기록조차 없었다. 결정 당시에는 verification README와 skill 참고 문서에만 적었다.

## 논의 흐름

1. **계기 — 자동 리깅 결정.** 사용자가 Mixamo 자동 리깅 결과를 올리며 말했다 `[대화]`: "자동 리깅이 훨씬 퀄리티가 높은 것 같은데. 네가 한번 직접 비교해봐." AI가 클로즈업으로 비교해 동의했고, 직접 경로는 중단했다. AI는 이 결론을 verification README와 `deform-qa.md` §5에 적었다. D 기록은 만들지 않았다.
2. **사용자의 문제 제기 — 경험을 매뉴얼로.** 다음 날 사용자가 시행착오 전체를 다시 쓸 수 있는 데이터베이스로 만들자고 했다. 핵심 요구는 세 가지였다.
   - 권장안을 먼저 보이고 경험을 분리할 것.
   - 타협 지점을 남길 것.
   - 시행착오를 처음 모델링부터 연결할 것.
3. **사용자의 기본 틀.** "어떤 작업을 진행하려고 하면 해결한 방법을 선택해라"와 같은 권장 문서를 먼저 두고, 실패와 비교 과정은 별도 문서나 세부 항목으로 둔다.
4. **AI 응답 — 조사 먼저.** 사용자 지시대로 조직·전문가의 지식 전환 방법론을 조사했다. 대상은 NASA LLIS와 GAO 감사, 육군 CALL OIL, ADR, IBIS/QOC, 패턴 언어, Toyota 한계 곡선·요코텐, Klein CDM, SRE 사후 분석, Diátaxis였다. 여기서 설계 규칙 12개를 뽑았다(`docs/playbook/00_DESIGN_RULES.md`).
5. **틀 검토.** 사용자 틀의 두 층 구조는 방법론과 일치해 유지했다. 다섯 가지를 더했다.
   - 작업 상황 색인: LLIS는 찾기 어려워 쓰이지 않았다.
   - 틀린 길 신호: Klein의 단서.
   - 타협 지점: 사용자 문제의식에는 있었으나 틀에는 칸이 없었다.
   - 강제 장치: "관찰됐지만 학습되지 않음".
   - 조건부 필수와 억지 기록 검사: QOC의 유지 비용과 저채택.
6. **연결성의 형식화.** 사용자가 원한 "처음 인체 모델링부터 자동 리깅까지 이어지는 이야기"를 노드 사슬로 만들었다. 각 노드가 `계기`(무엇이 불만이어서)와 `다음`/`왜 다음으로`(결과가 무엇을 불렀나)를 갖는다.
7. **검사기가 바로 쓸모를 보였다.** 첫 실행에서 J-001이 가리키는 D-056이 없다는 누락이 드러났다. 그래서 D-056을 사후 기록으로 만들었다. 검사기 자체 버그(한글 뒤 `\b`)도 함께 고쳤다.
8. **당시 기록과 사용자 회고의 차이.** 사용자는 고리·우윳빛 껍데기로 바꾼 이유를 "높은 퀄리티의 리깅을 보장할 수 없는 상황"으로 기억했다. 당시 문서의 근거는 골짜기 차단과 주제 적합이었다. 둘 중 하나로 고치지 않고 J-001 T2에 둘 다 적었다.

## 재사용 가능한 AI 사용 패턴

1. **경험 정리는 "다음 작업자가 무엇을 하나"와 "왜"를 다른 문서로 나눈다.** 사건 기록만으로는 작업 시작 시점에 찾을 수 없다.
2. **기록 양식을 만들 때 검사기를 같이 만들고, 검사기는 빠진 것과 억지로 채운 것을 함께 본다.** 조건부 필수(실패가 있으면 실패 절을 요구)로 빈칸 채우기 유인을 없앤다.
3. **사용자가 나중에 회고한 이유와 당시 기록이 다르면, 고쳐 쓰지 않고 둘 다 남긴다.**
4. **정리 작업에도 검사기를 바로 돌린다.** 첫 실행이 기존 기록의 누락(D-056)을 찾아냈다.

## AI가 기여한 것

- 방법론 조사와 설계 규칙 도출, 사용자 틀과의 차이 분석.
- 양식·검사기·자체 테스트 구현.
- 열흘치 운영 기록·커밋·verification을 시간순으로 꿰어 노드 사슬로 정리하고, 각 노드의 근거를 연결했다.

## 사용자가 기여한 것

- 문제 정의: 시행착오는 값진 매뉴얼이고, 타협이 품질 상한을 낮춘다.
- 기본 틀: 권장 먼저, 경험 분리, 연결성.
- 정리 범위를 정했다. 리깅만이 아니라 머리 모양, 고리·껍데기 표현까지 한 이야기로 묶으라고 했다.
- 여정 안의 판단 전환 네 번이 모두 사용자에게서 나왔다(R-023).

## 한계와 반사실 부재

- 조사는 공개 요약·2차 자료 위주다. 원 논문 전문은 읽지 않았다.
- 검사기는 통찰의 질을 판정하지 못한다. 사람 점검 다섯 항목을 `01_FORMAT.md` §4에 둔다.
- 이 시스템이 실제로 다음 작업의 시행착오를 줄이는지는 아직 측정 전이다. 측정 방법: 다음 사람·효과 작업에서 카드 확인 여부와 같은 실패 반복 여부를 WORKLOG에 적는다.
- J-001·J-002 외의 시행착오(서고 빛, 스크롤 영상 등)는 아직 정리하지 않았다. 이유는 README "정리 대기"에 적었다.
