# 레퍼런스 효과 기록 규칙 (Reference Effect Records) v1

작성: 2026-09-25 · 상태: **채택** (D-018, CASE-006)
적용: 레퍼런스 사이트의 연출·기술을 분석하는 모든 작업. `13_REFERENCE_GROUNDED_CREATIVE_MINING.md`(느낌·원칙 번안)와 짝을 이루며, 이 문서는 **"그 효과를 우리가 실제로 만들 수 있게 하는 정보"**를 담당한다.
자동 검사: `npm run records:check`가 `references/REF-*.md`의 필수 절과 효과 카드 필드를 검사한다.

---

## 0. 왜 기록하는가

> "이 기록 규칙은, 나중에 이 레퍼런스 수준의 고품질 UI/UX 설계 시스템에서 해당 레퍼런스들의 특징적인 효과를 구현하기 위해 필요한 정보들이 담겨 있도록 강제하는 용도야." — 사용자, 2026-09-25 `[대화]`

따라서 기록의 합격 기준은 **"이 문서만 읽은 다른 세션(사람 또는 AI)이 레퍼런스 사이트를 다시 열지 않고도, 그 효과를 우리 스택에서 같은 수준으로 재현할 계획을 세울 수 있는가"**이다.

이 목적에서 나오는 세 가지 원칙:
1. **효과 단위로 기록한다.** 사이트 소개나 감상이 아니라, 재현 대상인 "특징적 효과" 하나하나가 기록의 중심이다.
2. **관찰과 메커니즘을 분리한다.** 같은 관찰값이 다른 메커니즘에서 나올 수 있다(F-012). 녹화로 본 것, 소스로 확인한 것, 추론한 것을 구분한다.
3. **숫자와 재료를 남긴다.** "부드럽다", "고급스럽다"가 아니라 파라미터 값, 곡선, 입력 모델, 에셋 형식·용량을 남긴다. 재현의 품질은 이 숫자에서 결정된다(F-010).

## 1. 무엇을 기록 대상 효과로 고르는가

다음 중 하나에 해당하면 **효과 카드**를 만든다.

| 선정 이유 | 설명 |
|---|---|
| 사용자 지목 | 사용자가 녹화·대화에서 짚은 효과. **하나도 빠뜨리지 않는다** |
| wow 포인트 | 첫인상·기억에 남는 장면을 만드는 연출 |
| 장면 전환 | 두 장면을 잇는 전환(match cut, clip reveal, 페이드 등) |
| 재사용 메커니즘 | 다른 곳에도 쓸 수 있는 동작 원리(감쇠 회전, 지연 추종 스크롤 등) |
| 품질 차이 | 같은 사이트 안에서도 유난히 부드럽거나 끊기는 부분 — 비교 자료로 가치 있음 |

일반적인 폼, FAQ 아코디언, 푸터 등 재현 가치가 낮은 요소는 **장면·전환 지도에 한 줄**로만 남긴다.

## 2. 파일 구조

```
docs/uiux_system/references/
  README.md                 — 레퍼런스 목록과 레시피 색인
  REF-NNN_<SLUG>.md         — 레퍼런스 1개 = 파일 1개 (이 규칙의 필수 절)
  REF-NNN/                  — 선택: 측정 요약 JSON 등 작은 근거 파일
                              (사이트 에셋·스크린샷·원본 코드 사본은 넣지 않는다)
```

- 효과 ID: `EFX-NNN-MM` (레퍼런스 번호 + 효과 순번). 레시피 ID: `RCP-NN`.
- 저작권: 레퍼런스의 텍스처·모델·셰이더·영상·글꼴은 **저장소에 복사하지 않는다.** URL, 용량, 형식, 해시만 기록한다. 코드는 **메커니즘을 설명하는 짧은 발췌나 의사코드**만 쓴다.

## 3. 레퍼런스 파일의 필수 절

| 절 | 담아야 할 것 |
|---|---|
| `## 1. 레퍼런스 개요` | URL, 분석 날짜, 제작사(알 수 있으면), 사용자가 이 레퍼런스를 고른 이유와 원문 인용 |
| `## 2. 입력 증거` | 녹화 파일(길이·fps·중복 프레임 비율·촬영 규칙 준수 여부), 소스 확보 여부와 방법, 라이브 측정(도구·환경), 각 증거의 한계 |
| `## 3. 기술 스택과 전역 설정` | 프레임워크·라이브러리·버전, 렌더러 종류, 스크롤 엔진 설정값, ticker·동기화 방식, 코드 구성 방식(React 여부 등) |
| `## 4. 디자인 토큰` | 글꼴(이름·굵기·크기·자간·행간·대소문자), 주요 색, 배경, 버튼 형태 — 수치로 |
| `## 5. 장면·전환 지도` | 페이지 순서대로 모든 장면과 전환. 각 행에 녹화 시각, 섹션 selector, 입력 모델 요약, 해당 효과 카드 ID(없으면 "기록 제외 — 이유") |
| `## 6. 효과 카드` | §4 형식의 카드들 |
| `## 7. 에셋 목록과 조달 경로` | 레퍼런스가 쓴 에셋(종류·형식·해상도·용량·특수 처리) ↔ 우리가 같은 효과를 내기 위해 조달할 경로(`assets/registry.json` 후보) |
| `## 8. 성능·접근성·폴백` | 페이로드 합계와 큰 파일, 렌더 해상도 제한, 화면 밖 절전, 모바일 분기, reduced-motion 대응 여부, 실패 시 폴백 |
| `## 9. 레시피 후보` | 이 레퍼런스에서 뽑은 재사용 메커니즘. 다른 레퍼런스에서도 반복되면 `references/README.md`의 레시피 색인으로 승격 |
| `## 10. 열린 질문` | 확인하지 못한 것과 확인 방법 |

## 4. 효과 카드 형식 (필수 필드)

제목은 `### EFX-NNN-MM 이름`. 아래 **굵은 필드 이름**은 모두 있어야 한다. 알 수 없으면 값에 `미확인 — 이유`를 쓴다(빈칸 금지).

| 필드 | 담아야 할 것 | 왜 필요한가 |
|---|---|---|
| **선정 이유** | §1 표의 이유 + 사용자 발언이 있으면 인용 | 이 효과를 왜 재현하려는지 |
| **지각** | 관람자가 보고 느끼는 것을 시간 순서로 | 구현이 맞았는지 판단할 기준 |
| **입력 모델** | `시간` / `스크롤 위치` / `스크롤 속도` / `휠 충격` / `문턱 발동` / `포인터` / `로드` 중 해당하는 것(복수 가능) | 같은 모양도 입력 모델이 다르면 다른 구현 (F-012) |
| **판별 근거** | 입력 모델을 무엇으로 확정했는가 — 되돌리기 반응, 정지 시 반응, 소스 코드 | 추정을 사실로 오인하지 않기 위해 |
| **구현 메커니즘** | 렌더 층(WebGL/Canvas2D/DOM/CSS/영상), 레이어 구성, 핵심 로직의 의사코드 | 재현의 뼈대 |
| **파라미터** | 표: 이름 · 값 · 단위 · 출처(코드/측정/추론) | 품질을 결정하는 숫자 |
| **타임라인** | 구간(스크롤 거리·시간), 시작→끝 값, easing, scrub/지연, pin 길이 | 느낌을 결정하는 곡선 |
| **에셋** | 효과에 쓰인 파일의 종류·형식·해상도·용량·특수 처리(채널 패킹 등)·제작 도구 추정 | 재료 준비 |
| **성능 기법** | 해상도 제한, 절전, 캐시, 사전 워밍업 등 | 전시 PC에서 유지할 방법 |
| **접근성·폴백** | reduced-motion, 모바일, WebGL 실패 시 | 우리 계약(`04_VALIDATION`)과 대조 |
| **근거** | 주장별 증거 태그. 녹화 추정과 소스 확인이 다르면 둘 다 적고 정정 표시 | 신뢰도 |
| **재현 요구사항** | 우리 스택에서 필요한 패키지·에셋·사전 작업, 난이도(하/중/상) | 구현 계획의 입력 |
| **수용 기준** | 재현 성공을 판정할 측정 가능한 기준(예: 정지 후 0.7 s 안에 기본 속도 복귀) | 검증 기준 |
| **ECG 번안** | 어디에 쓸 수 있는지, 데이터 계약(LOW zone) 침범 위험 | 우리 목적과 연결 |
| **재현 상태** | `none` / `spike` / `verified` + 위치 | 진행 추적 |

## 5. 증거 규칙

- 증거 태그는 `10_RECORD_KEEPING.md`의 태그를 쓴다. 녹화는 `[영상]`, 소스 확인은 `[코드]`, 라이브 측정은 `[런타임]`, 추정은 `[추론]`.
- 녹화에서 추정한 뒤 소스로 확인했다면 **추정을 지우지 말고** "추정 → 실제" 형태로 둘 다 남긴다(판단 과정 보존).
- 녹화만 있고 소스가 없으면 입력 모델은 **판별 실험 결과**(D-017 순서의 되돌리기·정지·단발 입력)로만 확정한다.

## 6. 작성 절차

1. 증거 확보: D-017 규칙의 녹화 + 가능하면 소스(HTML·인라인 스크립트·셰이더) + 라이브 측정(네트워크 용량·글꼴·캔버스).
2. 장면·전환 지도부터 만든다(빠짐 방지).
3. 사용자 지목 효과 → wow → 전환 → 재사용 메커니즘 순서로 카드를 쓴다.
4. 에셋·성능·접근성 절을 채운다.
5. 레시피 후보를 뽑고, 기존 레시피와 겹치면 레시피에 사례를 추가한다.
6. `npm run records:check` 통과 후 커밋한다. 분석 대화가 끝나기 전에 커밋해 컨텍스트 압축으로 인한 손실을 막는다.

## 7. 완료 기준

- 장면·전환 지도에 페이지의 모든 장면이 있다.
- 사용자가 지목한 효과가 모두 카드로 있다.
- 모든 카드의 필수 필드가 채워져 있다(`미확인 — 이유` 허용).
- 입력 모델마다 판별 근거가 있다.
- `records:check` PASS.
