# 제약 기반 트레이드오프 탐색 (tradeoff-study)

업계 용어로는 시스템 공학의 **trade study / 대안 분석(AoA)**, 소프트웨어 아키텍처의 **ATAM(아키텍처 트레이드오프 분석)**, 제조의 **가치 공학(기능 분석)**, 그래픽스·하드웨어의 **근사 컴퓨팅 / 지각 기반 최적화**, 최적화 이론의 **설계 공간 탐색(파레토)**이 각각 이 작업의 한 부분을 다룬다. 이 스킬은 그것들을 하나로 묶는다. 근거와 출처는 `references/sources.md`.

핵심 질문은 하나다: **"잃어도 아무도 모르는 것은 무엇이고, 그것을 잃는 대가로 무엇을 얻을 수 있나?"**

## 언제 쓰나

| 규모 | 조건 | 깊이 |
|---|---|---|
| 생략 | 한 줄 수정, 선택지가 하나, 이미 D 기록으로 확정된 방식 | 쓰지 않는다 |
| 가벼움 (LOW) | 방식이 둘 이상이지만 되돌리기 쉽고 영향이 한 파일 안 | 보고 3줄(권장 · 잃는 것 · 뒤집히는 조건) |
| 표준 (MEDIUM) | 화면 효과, 성능 문제, 새 파이프라인, 여러 파일 | 아래 1–9단계 전체, `references/report_template.md` 보고 |
| 심화 (HIGH) | 되돌리기 어렵거나(자산 파이프라인, 데이터 계약, 외부 의존) 전시 성능을 좌우 | 전체 + 측정 2종 이상 + D 기록 필수 |

사용자가 이미 한 가지 방식을 제안했어도 건너뛰지 않는다. 그 제안을 후보 하나로 넣고 같은 기준으로 잰다.

## 절차

### 1. 목표 기능 — 사용자가 실제로 받아야 하는 것 (가치 공학)
- "무엇을 만드나"가 아니라 **"무엇이 보이고·느껴지고·전달되어야 하나"**를 동사+명사로 적는다. 예: "스크롤에 따라 바뀌는 빛 커튼이 보인다", "파형이 끊기지 않는다".
- 기능마다 **필수 / 있으면 좋음 / 없어도 됨**을 붙인다. 사용자 발화가 근거면 인용한다.
- 지금 구현이 하는 일 중 어느 기능에도 연결되지 않는 것은 "비용만 있는 일"로 표시한다.

### 2. 제약 — 깨면 안 되는 것과 환경
- **하드 제약**: 데이터·파형·단위·Reference/Difference 계약, 사용자 확정 결정(D 기록), 접근성, 대상 장비. 하나라도 어기는 후보는 점수와 상관없이 탈락한다(가중합으로 상쇄 금지).
- **소프트 제약**: 예산(프레임 시간, 메모리, 로딩, 작업 시간), 유지 비용.
- **동시 부하 지도**: 같은 순간에 무엇이 함께 도는가(예: 실시간 처리 + 파형 + 배경). 가장 무거운 겹침 구간이 설계 기준점이다. 겹치지 않는 구간에는 여유가 있다.
- **이전 검증**: F/D/O/R·playbook·verification에서 같은 기법을 이미 시험했는지 먼저 찾는다(`grep` 기법 이름·효과 이름). 사용자가 기억하는 과거 결함이 있으면 기록과 대조해 사실 관계를 확인한다.

### 3. 여유 지도 (slack map) — 품질을 낮춰도 손해가 아닌 곳
아래 축마다 **잰 값**을 적는다(못 재면 `[추정]`).
- **공간**: 화면 중 UI가 덮는 비율, 덮개의 불투명도, 화면 밖, 가장자리.
- **밝기·대비**: 어두워서 안 보이는 구간, 커튼·블러·안개 아래.
- **시간**: 잠깐만 보이는 순간, 전환 중, 재생 중(눈이 데이터에 가 있음).
- **주의**: 사용자의 시선이 가는 곳(데이터, 조작 대상) vs 배경.
- **정밀도**: 정확한 값이 아니라 인상만 필요한 것(분위기, 장식).
- **변화 빈도**: 안 바뀌거나 드물게 바뀌는 것(정적 조명, 고정 경로, 고정 시점).
- **범위**: 실제로 쓰이는 입력 범위(예: 마우스 회전 ±3°만 씀, 스크롤 범위 0).
사용자가 "이 정도면 충분"이라고 말한 수준은 여유 지도의 가장 강한 근거다. 그대로 인용한다.

### 4. 기준 — 품질과 성능을 각각 여러 축으로
한 숫자로 뭉치지 않는다. 축마다 **문턱값**(이 정도면 통과)을 둔다.
- 품질: 영역별 충실도(필수 기능이 보이는 영역 / 배경), 시간 안정성(깜빡임·떨림), 결함 유형(이중상, 늘어짐, 계단, 밴딩), 다른 화면과의 일관성, 데이터 정확성.
- 성능: 평균 프레임 시간, 최악 프레임(끊김), 동시 부하 구간의 여유, 로딩 시간, 메모리·VRAM, 파일 크기.
- 비용: 구현 시간, 자산 파이프라인 유지, 바꿀 때 다시 해야 하는 일, 위험, 되돌리기 쉬움.
가중치는 마지막 동점 처리에만 쓴다. 선택은 3–7단계의 필터와 지배 관계가 먼저다.

### 5. 질문 — 답에 따라 결론이 바뀔 때만
- 여유 지도나 하드 제약에 빈칸이 있고 **그 답이 순위를 바꿀 때만** 묻는다. 최대 3개, AskUserQuestion으로 선택지를 붙여 묻는다.
- 바꾸지 않으면 묻지 않고 가정으로 적은 뒤 진행한다(보고서 "가정" 칸).

### 6. 후보 만들기 — 레버 카탈로그로 넓히기
- 이미 나온 안(사용자 제안, 기존 구현 = 현상 유지)을 먼저 적는다.
- `references/levers.md`의 레버 L1–L12를 하나씩 대보며 "이 레버를 여유 지도의 어느 칸에 걸 수 있나"를 묻는다. 걸리는 칸이 있으면 후보로 만든다.
- 단일 레버 후보 뒤에 **조합 후보**를 만든다. 대개 정답은 "필수 기능 영역은 그대로, 나머지는 레버 2–3개 겹치기"다.
- 대담한 후보를 하나 이상 넣는다(표현 바꾸기, 요구 재정의). 탈락하더라도 왜 탈락했는지가 보고 가치다.

### 7. 거르기와 고르기
1. **하드 필터**: 하드 제약을 어기는 후보 탈락.
2. **지배 제거(파레토)**: 모든 기준에서 다른 후보보다 같거나 나쁜 후보 탈락.
3. **손해-여유 대응**: 남은 후보마다 잃는 것을 하나씩 적고, 그 손해가 여유 지도의 어느 칸에 떨어지는지 표시한다.
   - `무료` — 여유 칸 안에 떨어짐(보이지 않거나 사용자가 필요 없다고 함).
   - `싸다` — 여유 밖이지만 문턱값 안.
   - `실손` — 필수 기능이나 문턱값을 건드림.
4. **고르기**: `실손`이 없는 후보 중 성능·비용 이득이 가장 큰 것. 없으면 `실손`이 가장 작은 둘을 사용자에게 진짜 트레이드오프로 제시한다(결정권은 사용자).
5. **민감도**: 어떤 가정·측정값이 바뀌면 순위가 뒤집히는지 적는다. 그것이 D 기록의 "되돌려야 하는 조건"이 된다.

### 8. 검증 — 추정을 측정으로
- 순위를 가르는 수치부터 잰다. 같은 장면·같은 프레임·같은 측정기(R-024). 비교 렌더는 잡음(디더·grain)을 고정한다(F-019).
- 이 클라우드 환경은 소프트웨어 렌더(SwiftShader)라 **상대 비교만** 유효하다. 절대 프레임 시간은 사용자 PC 확인 항목으로 남긴다.
- 증거 태그: `[측정]` `[계산]` `[코드]` `[기록]` `[추정]`. 추정을 측정처럼 쓰지 않는다.

### 9. 보고와 기록
- `references/report_template.md` 순서로 보고한다(채팅은 한국어). 첫 줄은 권장안 + 얻는 것 + 잃는 것.
- 구현을 시작하면 같은 내용으로 D 기록을 먼저 쓴다(갈림길·검토한 선택지·고른 것과 근거·버린 것과 이유·되돌려야 하는 조건이 7단계와 1:1로 대응).
- 사용자가 결론을 받아들이면 playbook 카드/여정을 갱신한다(AGENTS.md "Experience playbook").
- 보고서 사례는 `examples/`에 남긴다. 다음 비슷한 작업은 사례의 여유 지도부터 재사용한다.

## 하지 말 것
- 주어진 선택지만 비교하고 끝내기(기존 의사결정 스킬의 한계 — `references/sources.md` §3).
- 하드 제약 위반을 다른 점수로 상쇄하기.
- "실시간이 아니면 안 된다 / 영상이면 안 된다" 같은 표현 수단 고정. 굽기·캐시·근사는 항상 후보다.
- 여유 지도를 재지 않고 "안 보일 것"이라고 단정하기.
- 사용자 승인 없이 요구(기능 자체)를 줄이기 — L12는 질문으로만 쓴다.
