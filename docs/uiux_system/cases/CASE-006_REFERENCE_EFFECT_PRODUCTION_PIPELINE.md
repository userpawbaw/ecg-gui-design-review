# CASE-006 — 레퍼런스의 wow를 "재현 가능한 기록"으로 바꾸기까지

작성 기준: 2026-09-25 (2026-09-26 §6 추가)
상태: **방법론 변경 구현** (레퍼런스 효과 기록 규칙 채택, 제작 파이프라인 채택 여부 P1은 미결)
관련 운영 기록: `F-010`, `F-011`, `F-012`, `D-017`, `D-018`, `F-017`, `D-019`, `D-020`, `D-021`; 선행: `F-009`, `D-015` (그리고 `feat/attract-vnext-recovered-20260924` branch에만 있는 Attract 결정)

> 아래 직접 인용은 이 세션에서 확인 가능한 사용자 발화다 `[대화]`. 전체 machine-export transcript는 아니다.

## 배경

CASE-005에서 creative 경로를 Alpha(구현 인지)/Beta(이미지 우선)로 바꾼 뒤에도, 결과물이 우수 레퍼런스의 연출 수준에 미치지 못한다는 문제가 남았다. 이 CASE는 그 원인을 "발상"이 아닌 "제작 정보와 재료의 부재"로 재정의하고, 레퍼런스 분석을 재현용 기록으로 강제하는 규칙을 만든 과정이다.

## 논의 흐름

### 1. 사용자가 문제를 "백엔드적 체계"로 재정의했다

> "wow 포인트를 제대로 살리지 못하는 감이 있더라고. 때문에 유사 효과를 만드는 데 필요한 에셋이나 사전 구축할 자료 … 필요 기술 스택 확인 등 좀 더 백엔드적으로 체계를 더 구축할 필요가 있다고 느꼈어."

AI는 원인을 여섯 가지 빈칸(Canvas 2D 상한, 에셋 계층 없음, timeline 엔진 없음, 정지 이미지 분석, 전시 입력 번안 없음, 연출 QA 없음)으로 진단하고, three.js + GSAP + Lenis spike로 메커니즘을 확인했다(F-010).

### 2. 녹화가 AI의 첫 해석을 뒤집었다

AI는 캡처 1장과 사이트 태그로 "지구 회전"을 크게 구현했다. 사용자가 녹화를 제공하자, 실제 wow는 역광과 지구 → 선 → 카드 모서리로 이어지는 match cut이라는 것이 드러났다(F-011).

### 3. 사용자가 관찰을 날카롭게 질문했다

> "스크롤 할 때의 빠른 속도 회전과 멈췄을 때의 느린 속도 회전 간의 전환이 부드러워. 이건 어떻게 구현한 걸까?"

> "38~39초에 스크롤 잠시 멈추는 걸 보면 좀 끊기는 것처럼 보이지 않아?"

AI는 녹화를 60 fps로 풀어 상관·감쇠를 측정했고, 사용자는 촬영 규칙을 제안했다("먼저 스크롤을 멈추고 정지 상태의 효과를 본 뒤 규칙적으로 스크롤"). 순서는 고정하고 시간은 대략으로 하는 D-017이 이렇게 정해졌다.

### 4. 소스 확인이 녹화 기반 추정을 다시 정정했다

네트워크 허용 뒤 소스를 읽으니, "속도 비례 회전"은 위치 연동 + `scrub: 1`이었고, 부드러운 감속은 원통 갤러리의 wheel 충격 + 감쇠였다(F-012). 같은 관찰값이 다른 메커니즘에서 나올 수 있다는 것이 확인되었다.

### 5. 사용자가 기록의 목적을 못박았다

> "기록 없이 분석만 진행하면 컨텍스트 오염 가능성이 있으니, 기록 규칙이 확정되면 첫번째 사이트 분석을 기록 규칙에 맞게 작성해."

> "이 기록 규칙은, 나중에 이 레퍼런스 수준의 고품질 UI/UX 설계 시스템에서 해당 레퍼런스들의 특징적인 효과를 구현하기 위해 필요한 정보들이 담겨 있도록 강제하는 용도야."

AI는 이를 "문서만 읽고 사이트를 다시 열지 않아도 재현 계획을 세울 수 있는가"라는 합격 기준으로 옮기고, 효과 카드 15개 필드와 자동 검사를 설계했다(D-018).

### 6. 사용자가 "한 장"의 검증을 "구간"의 검증으로 바꿨다 (2026-09-26)

AI는 REF-003 경로를 캡처 1–2장과 진행률 숫자로 확인하고 재현 완료로 보고했다. 사용자는 결과를 보고 원인까지 짚었다.

> "표시지점 뒤, 즉 위치 표시기가 이동한 곡선을 이미 지난 경로라는 것을 알 수 있게 다른 색으로 확실하게 표시해줬는데, 우리 구현에서는 그 부분의 디테일이 부족하네. … 아마도 여러 장을 확인하지 않아서 그런 느낌. 한 대여섯장 이상은 확인해봐야 할 것 같은데?"

AI는 처음에 색 대비 문제 하나로 보았으나, 12장 대조에서 결함이 세 개(대비, 구간 중간의 표시기 이탈, 수정 후 나타난 dash 분할)였다(F-017). 같은 턴에 사용자는 다락방 결과를 보고 "빛 효과 말고도 3d 작업시 셰이더나 후처리를 항상 검토하도록" 요청했다. 두 요청은 "빠진 층을 체계적으로 찾는 검증"이라는 같은 규칙으로 묶였다(D-019, 체크리스트 §12, 21번 §8).

사용자는 외부 UI 컴포넌트가 "직접 만드는 경우보다 나을 지 아닐 지 확실히 알고 싶"다고 했다. AI는 의견 대신 같은 데이터로 두 변형을 만들어 같은 12장 규칙으로 판정했고, 컴포넌트는 wow 포인트(정지 소나)에서 FAIL, 번들 2배 이상이었다 — 외부 컴포넌트는 기법 공급원으로 둔다(D-021). 에셋 조달처도 같은 방식으로 "접근·라이선스·자동 받기"를 실제로 시험한 뒤 순서에 넣었다(D-020).

## 사용자가 기여한 것

- 문제를 창의성이 아닌 제작 체계(에셋·3D 형식·기술 스택)의 문제로 재정의.
- 녹화 제공, 정지·스크롤 반응의 차이와 끊김을 직접 지목(카드 감속의 부드러움, 타이포 끊김).
- 촬영 규칙의 핵심 아이디어(정지 먼저, 입력 표시)와 "시간은 대략, 순서는 고정" 합의.
- 비영리 학술 전시라는 라이선스 판단 근거, 네트워크 허용 설정.
- 기록의 목적과 "컨텍스트 오염" 위험 지적 → 기록 규칙의 존재 이유 확정.
- 검증 단위를 "한 장"에서 "구간 6장 이상"으로 바꾼 지적, 3D 셰이더·후처리 상시 검토 요청, 외부 컴포넌트·에셋 조달처를 실험으로 판정하라는 요구.

## AI가 기여한 것

- 여섯 가지 빈칸 진단, spike 구현과 headless 검증, 에셋 registry·fetch 파이프라인.
- 녹화 정량 분석(60 fps 분해, 상관·감쇠 측정, 녹화 프레임 중복 발견), scroll HUD와 로컬 캡처 스크립트.
- 소스 분석으로 스택·파라미터 확인, 자기 해석의 정정(F-011, F-012)을 기록으로 남김.
- 기록 규칙(21번) 설계와 자동 검사 구현, REF-001 작성.
- 12장 대조 도구(`route-compare.mjs`·`sonar-compare.mjs`), follow 매핑 해법, A/B 컴포넌트 비교와 비용 측정, ambientCG·Openverse 자동 받기.

## 구축된 시스템

```text
녹화(D-017 순서 + HUD) ─┐
소스(HTML·인라인 JS·셰이더) ├→ REF-NNN 기록(21번 규칙)
라이브 측정(네트워크·글꼴) ─┘     ├ 장면·전환 지도 (모든 장면, 카드 ID)
                                ├ 효과 카드 EFX (입력 모델·판별 근거·파라미터·타임라인·에셋·수용 기준 …)
                                ├ 에셋 ↔ 우리 조달 경로 (assets/registry.json)
                                └ 레시피 후보 → references/README.md 레시피 색인
records:check가 필수 절·필드·입력 모델 어휘·재현 상태·근거 태그·지도 연결을 검사
```

## 재사용 가능한 AI 사용 패턴

1. **관찰 → 판별 실험 → 소스 확인의 3단 검증.** 녹화의 상관계수는 메커니즘을 확정하지 못한다. 되돌리기·정지·단발 입력으로 판별하고, 가능하면 소스로 확인한다.
2. **자기 정정을 기록으로 남긴다.** 틀린 추정을 지우지 않고 "추정 → 실제"로 남기면, 다음 분석에서 같은 오판을 막는 규칙이 된다.
3. **분석의 합격 기준을 "재현 가능성"으로 둔다.** 감상이 아니라 숫자·재료·수용 기준이 남았는지를 기계로 검사한다.
4. **컨텍스트 압축 전에 커밋한다.** 긴 분석은 대화가 아니라 저장소에 남아야 다음 세션이 이어받는다.
5. **"나을까?"라는 질문은 같은 데이터·같은 판정 기준의 A/B로 답한다.** 의견보다 12장 대조와 번들 측정이 결론을 빨리 낸다.

## 한계

- 사이트 소스가 번들·난독화되어 있거나 WebGL 없이 영상으로 만든 사이트에서는 파라미터 확보가 어렵다. 이때 카드는 `미확인 — 이유`가 많아진다.
- 자동 검사는 필드의 존재와 형식만 본다. 값이 정확한지는 사람이 검토해야 한다.
- 실제 GPU 성능은 이 클라우드 환경에서 측정하지 못한다.
- 제작 파이프라인 전체 채택(P1)은 레퍼런스 2~3개를 더 분석한 뒤 결정하기로 했으므로, 이 CASE는 기록 규칙까지만 확정한다.
