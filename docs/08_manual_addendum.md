# 재사용 GUI 설계 매뉴얼 · 이번 검토에서 보강할 규칙

2026-09-09. 기존 매뉴얼의 시각 계층·단계 공개·기능적 모션·요소 역할·화면 분리 원칙은 유지한다. 다음은 실제 제작과 검증 사이에서 발견한 빈틈을 보강하는 부록이다. ECG 밖의 데이터 분석·계측·관리 프로그램에도 적용할 수 있다.

## 1. 요소의 존재와 증거의 존재를 구분한다

각 화면의 완성도를 네 단계로 나눈다.

| 단계 | 확인할 것 | 충분하지 않은 증거 |
|---|---|---|
| 구조 | 필요한 상태와 컨트롤이 있는가 | 파일명·프레임 개수만 센 결과 |
| 동작 | 실제 조작 후 올바른 상태로 바뀌는가 | 클릭 핸들러가 있다는 소스 검색 |
| 근거 | 값·출처·계산 범위가 실제 자료와 일치하는가 | SAMPLE 배지 옆의 성공 문구 |
| 환경 | 목표 브라우저·장치·배율·키보드에서 사용할 수 있는가 | DOM 에뮬레이터 통과 |

PASS를 한 열에 합치지 않는다. “프레임 16개 존재”와 “장치 연결 상태 16개 실기 검증”은 다른 주장이다. 미구현, 검사 실패, 검사를 못 한 상태도 각각 구분한다.

## 2. 화면 추가의 선택지를 넓힌다

검토 결과는 `유지 / 수정 / 삭제 / 통합 / 분리 / 추가 / 연결 대기`로 기록한다. 추가는 다음 두 경우 모두 가능하다.

- 현재 과업에서 필요한 정보·행동이 빠졌다.
- 개별 화면의 결함이 없어도 다른 사용자 질문, 데이터 범위, 시간축, 오류·복구, 독립 작업 수명 때문에 새 공간이 필요하다.

방법 선택과 그 설명처럼 동시에 봐야 하고 같은 조건을 공유하면 패널을 우선한다. 개별 사례와 전체 집계처럼 결론의 표본·범위가 달라지면 화면 분리를 검토한다. 분리할 때는 전환 전후에 유지할 문맥과 새로 표시할 출처를 정의한다.

새 화면 제안에는 목적, 사용자, 진입/복귀, 필요한 근거, 기존 기능으로 부족한 이유, 기본/오류 상태, 완료 과업을 적는다. 필요한 데이터가 아직 없으면 기능의 자리는 설계하되 실제 성공 상태를 만들어 채우지 않는다.

## 3. 작은 배지에도 근거 계약을 붙인다

`LIVE`, `검증 완료`, `동일 입력`, `최신`, `정상`은 장식이 아니라 사실 주장이다. 표시 조건과 해제 조건을 문서화한다. transport 연결과 source 유형, 자료 보관 시점과 현재 코드 재현, selected와 success를 구분한다.

모르는 값은 null/미측정/참조 없음으로 표시한다. 0이나 초록 점으로 바꾸지 않는다. 시뮬레이션이 필요하면 해당 값이나 파형 바로 옆에 표시한다. 화면 어딘가의 SAMPLE 배지 하나로 다른 확정 문구를 정당화하지 않는다.

## 4. 비교 GUI는 유지해야 할 조건을 먼저 정한다

방법 변경 때 유지할 입력·시간·단위·진폭, 조건 변경 때 바뀔 수 있는 record, 전체 결과로 이동할 때 바뀌는 집계 범위를 정한다. 비교 대상마다 자동으로 축을 맞추면 실제 차이가 숨겨질 수 있다.

지표는 이름·식·단위·전처리·표본 구간·참조·집계 단위·누락 처리와 함께 정의한다. 값이 개선됐다는 이유만으로 정성적 성공을 단정하지 않는다. 국소 사례와 전체 집계, 표준편차와 CI, 미유의와 동등성을 혼용하지 않는다.

## 5. 모션에도 데이터 진실성 조건을 넣는다

기존의 `trigger → 대상 → 의미 → 시간 → 중단 → reduced-motion`에 **움직여도 되는 것과 그대로여야 할 값**을 추가한다. 선택색·패널 위치는 전환할 수 있지만 실제 측정값의 중간 상태를 보간해 존재하지 않는 출력으로 보여주면 안 되는 경우가 있다.

이미 저장된 결과를 바꿀 때 가짜 처리 진행률은 필요하지 않다. 실제 작업이 비동기라면 run identity,취소,오래된 결과 폐기,부분 실패를 설계한다. 반복 모션의 기본값과 화면을 떠났을 때 중지 규칙도 정한다.

## 6. 비교 평가의 독립성을 기록한다

기존안을 개선하려는 새 안은 먼저 프로젝트 원본 목표·제약으로 설계하고, 공통 rubric과 함께 동결한 뒤 비교한다. 기억을 완전히 지웠다고 주장하지 않는다. 이전 파일 열람 시점, 동결 commit, 동일 평가 과업을 기록한다.

모델 등급·작업 시간·파일 수·자기 점수는 품질 증거로 사용하지 않는다. 기존안의 장점과 새 안의 약점을 같은 수준으로 적는다. 실제 렌더를 보지 못했다면 시각적 우월성도 유보한다.

## 7. 팀 문서는 설명과 디버깅을 연결한다

구성요소마다 최소한 `ID / 역할 / 존재 이유 / 입력→출력 / 유지 조건 / 오류 상태 / 첫 확인 위치`를 적는다. 사용자 화면에는 불필요한 내부 ID를 크게 노출하지 않는다. 버그 보고에는 조건·source·버전·예상/실제·환경을 포함한다.

이전 명세의 ID를 재배정했다면 매핑을 남긴다. 문서의 요소 목록과 실제 DOM/컴포넌트 목록을 대조한다. 구현되지 않은 adapter·메타데이터는 “향후 계약”이라고 적어 이미 연결된 것처럼 읽히지 않게 한다.

## 8. 중단과 재개를 작업 절차에 포함한다

각 의미 있는 단계 뒤에 PLAN/WORKLOG를 갱신하고, 승인된 저장소에 커밋한 뒤 원격 파일 해시를 확인한다. 새 프로젝트에서도 저장소의 AGENTS와 아래 템플릿을 가져오면 같은 방식으로 운영할 수 있다. 이는 프로젝트 작업 규칙이며 사용량 제한 중에도 계속 실행되는 자동화 서비스는 아니다.

```text
단계 / 목표:
기준 자료·버전:
작성·변경 파일:
실제로 수행한 검사와 증거:
판정: PASS / CONDITIONAL / FAIL / NOT VERIFIED
계획상 완료된 범위:
남은 구현·검증·불확실성:
다음 한 단계:
원격 commit·내용 확인:
```

재개할 때는 최신 원격 commit, 계획의 마지막 단계, 로컬 파일 존재와 변경분, 동결 파일 해시, 오래된 빌드 여부를 검사한다. 의도적 미커밋 변경과 손실을 혼동하지 않는다. 작성 파일이 남아 있어도 임시 실행 세션·메모리 캐시까지 복구됐다고 말하지 않는다.
