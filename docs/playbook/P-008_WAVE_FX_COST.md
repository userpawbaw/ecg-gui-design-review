## 권장 방법
1. 먼저 잰다: `node verification/wave-fx-20261108/bench.cjs live 1 cpu`. 비교는 **프레임당 CPU(CPU % ÷ 초당 그리기)**, 같은 회차 안의 비율로.
2. 표본은 화면 폭 링 캔버스에 도착할 때 한 번만 긋는다(`src/waveStrip.ts` `StripRow.update`: 이음점 오른쪽만 지우고 다시 잇기).
3. 나이에만 달린 효과(잔광 흰빛 · 선단 앞 사라짐)는 1 px 램프로 미리 굽고 선단 창에만 붙인다(`composeRow`). 흰빛 창은 3τ = 0.6 s.
4. 선단 앞 빈칸은 링에서 미리 비운다(`clearAhead`).
5. 번짐 ½ · ¼ · ⅛는 새 띠만 갱신하고 ½ 한 장으로 미리 더한다. 번짐 층은 dpr과 무관하게 CSS ½ 해상도.
6. 정적 층(격자 · 눈금)은 축 · 크기가 바뀔 때만 만들고 캔버스 CSS 배경으로 붙인다(`live/livePlotFx.ts` `paintStatic`, 실시간 스윕 프레임당 CPU −11 %).
7. 느린 PC 안전장치: 그리기 간격이 26 ms 넘게 이어지면 번짐 단계를 2 → 1 → 0으로 낮추고 다시 올리지 않는다.

## 도달한 품질
실험실 탭은 기존 그리기 대비 프레임당 CPU 0.63배, 초당 그리기 25 → 34회. 모양은 같다(밝은 화소 수 ±35 % 시험). 사용자 확인 `[대화]` "모두 최적화 적용 버젼으로".

## 가지 말 길
- **효과 코드를 계열마다 그대로 복사하기** — 계열 수만큼 비용이 곱해져 4계열 29 fps, 중첩 16 fps(J-005 T1). 계열이 1 ~ 2개뿐이면 다시 열 수 있다.
- **경로만 줄이고 화소 면적은 그대로 두기** — 링에 한 번만 그어도 행 크기 층에서 붙이기를 14번 하면 비용이 같다(J-005 T2).

## 틀린 길이라는 신호
- 최적화했는데 CPU가 그대로다 → 단계별로 재면 합성 시간이 화면 화소 수에 비례한다(J-005 T2, T4).
- dpr 2 화면에서만 느리다(J-005 T3).

## 적용 범위와 재검토 조건
- 범위: 표본 x가 고정되는 캔버스 2D 파형(스윕 · 스크롤). 구간 고정 · 정지 화면은 원래 경로로 한 번 그린다.
- 다시 열 조건: GPU가 있는 전시 PC에서 원래 방식(`?wave=prev`)도 4계열 · 중첩에서 55 fps 이상이면 단순한 쪽을 다시 본다. 표본 x가 매 프레임 바뀌는 확대 · 이동 화면에는 맞지 않는다.

## 남은 한계
- GPU가 있는 PC에서의 절대값은 재지 않았다(이 환경은 소프트웨어 래스터).
- dpr 2에서는 자동 낮춤이 번짐을 끈 뒤에도 이전 그리기보다 느리다(26.5 대 35 fps).
