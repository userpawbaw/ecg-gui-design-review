# UI/UX 기록 규약 — 결론이 아니라 판단 경로를 남긴다

상위 기준: `00_UIUX_MASTER.md`  
원형 참고: `userpawbaw/ECG_denoising_method_comparision`의 `docs/19_record_keeping.md`, `docs/17_checklists.md`, `scripts/check_records.py`, `docs/40~42` AI 협업 사례 문서.

> **왜 필요한가.** 이 프로젝트에서 중요한 산출물은 최종 화면만이 아니다. 어떤 화면이 밋밋하다고 느꼈는지, 무엇을 먼저 제안했는지, 왜 어떤 아이디어를 기각했고, 어떤 근거가 판단을 바꿨는지까지 남아야 다음 AI·다음 세션·포트폴리오 독자가 같은 결론을 다시 검증할 수 있다.
>
> **첫 번째 독자는 AI가 아니라 사람일 수 있다.** 특히 방법론 CASE는 사용자가 몇 달 뒤 다시 읽어도 `문제 제기 → AI 응답 → 반론 → 판단 변화 → 구축 결과`를 복원할 수 있어야 한다. provenance가 맞아도 이 흐름이 사라졌다면 기록 품질은 충분하지 않다.
>
> 가장 중요한 세 줄:
>
> 1. **기각한 후보와 틀린 초기 판단을 지우지 않는다.** 조용히 고쳐 쓰지 않는다.
> 2. **중요한 결정은 구현 전에 기록한다.** 무엇을 골랐는지보다 **무엇을 왜 버렸는지**가 기록의 값이다.
> 3. **방법론 CASE는 인간이 다시 읽을 수 있을 만큼 구체적으로 쓴다.** 중요한 대화 원문이 있으면 짧게 인용하고, 없으면 `[재구성]` 또는 `기록 없음`으로 정직하게 표시한다.

## 1. 운영 기록 네 종류

| 종류 | 파일 | 담는 것 | 판별 질문 |
|---|---|---|---|
| **F — Finding** | `records/F_FINDINGS.md` | UI/UX 해석을 바꾼 발견 | "이걸 몰랐다면 잘못된 디자인 판단이 굳었는가?" |
| **D — Decision** | `records/D_DECISIONS.md` | 갈림길에서 고른 설계·도구·운영 방식 | "다르게 골랐다면 경험·구현·검증 결과가 의미 있게 달라졌는가?" |
| **O — Incident** | `records/O_INCIDENTS.md` | 결과를 바꾸지는 않아도 시간·재현성·협업 품질을 잃게 한 사고 | "같은 일이 또 나면 다시 시간을 잃는가?" |
| **R — AI Collaboration Review** | `records/R_AI_COLLABORATION.md` | Chat/Work/Codex/Plugin/Skill을 쓰는 방식 자체의 교훈 | "이건 UI 그 자체보다 AI를 쓰는 방법에 관한 교훈인가?" |

F/D/O/R은 서로 복사하지 않는다. 필요한 경우 다른 항목 ID를 참조한다.

### F와 D의 경계
- "Awwwards식 표현은 core waveform 전체에 넣기 어렵다"는 **발견**일 수 있다.
- "Attract/Transition은 HIGH, waveform inspection은 LOW Creative Freedom으로 운영한다"는 **결정**이다.

### O와 R의 경계
- stale global lock 때문에 다른 작업이 막힌 것 자체는 **O**다.
- 사용자의 오해를 검증하지 않고 global mutex로 일반화한 AI 협업 방식의 교훈은 **R**이다.

## 2. F 템플릿 — 판단이 바뀐 과정을 남긴다

```markdown
## F-001. 한 줄 요약

| | |
|---|---|
| 상태 | 확정 / 잠정 / 철회 |
| 발견 | 날짜 · 관련 commit/PR/대화 |
| 영향 | 어떤 디자인 판단이 어떻게 바뀌었는가 |

### 발단 — 무엇이 이상해 보였나
### 먼저 의심한 것과 배제 방법
### 결정적 근거
### 조치와 검토한 대안
### 비용 / 영향 범위
### 놓쳤다면
### 일반화
```

필수는 **발단 / 먼저 의심한 것과 배제 / 결정적 근거 / 놓쳤다면**다. 당시 기록이 없으면 추정해서 채우지 말고 `기록 없음`이라고 쓴다.

---

## 3. D 템플릿 — 고른 것보다 버린 것을 남긴다

```markdown
## D-001. 무엇을 정했나

| | |
|---|---|
| 시점 | 날짜 · commit/PR |
| 상태 | 유효 / 번복됨(→ D-nnn) |
| 연결 | 관련 F/O/R |
| CASE | CASE-nnn 또는 불필요 — 구체적 사유 |

### 갈림길 — 무엇을 정해야 했나
### 검토한 선택지
### 고른 것과 근거
### 버린 것과 이유
### 되돌려야 하는 조건
```

**기록 시점은 구현 전**이다. 결과가 나온 뒤에 작성하면 기각 후보가 사라진다.

작은 spacing 값 조정처럼 상위 결정의 범위 안에서 반복 튜닝하는 작업은 매번 D로 만들지 않는다. 단, 레이아웃 구조·정보 위계·파형 의미·navigation·motion language·도구/워크플로우처럼 결과의 성격을 바꾸는 갈림길은 D 대상이다.

---

## 4. O 템플릿 — 짧게 쓰고 재발 방지로 끝낸다

```markdown
## O-001. 무엇이 일어났나

| | |
|---|---|
| 시점 | 날짜 · commit/PR |
| 잃은 것 | 시간 / 재현성 / 검증 / 협업 |
| 재발 방지 | 문서 / 테스트 / 구조 변경 |

### 증상
### 원인
### 조치
### 재발 방지와 자동화 상태
```

O의 목적은 회고 자체가 아니라 **재발 방지책이 실제 규칙·테스트·구조로 승급됐는지** 확인하는 것이다.

---

## 5. R 템플릿 — AI 사용 방법의 교훈만 남긴다

```markdown
## R-001. 한 줄 요약

| | |
|---|---|
| 대상 | 어떤 AI/Plugin/Skill 산출물 또는 협업 과정인가 |
| 처리 | 채택 / 부분 채택 / 폐기 / 보류 |
| 연결 | 관련 F/D/O |
| CASE | CASE-nnn 또는 보류 — 구체적 사유; 재검토: 조건 |

### AI/도구가 내놓은 것
### 사람이 문제 삼은 것
### 검증 방법과 결과
### 재사용 규칙
```

**`재사용 규칙`이 없으면 R로 남길 가치가 없다.** 프로젝트 결과에 관한 교훈이면 F/D/O로 보낸다.

예: "creative tool을 평가할 때 가장 엄격한 core data view만 보지 말고 user journey의 Creative Freedom Zone을 먼저 나눈다."

## 6. 근거 등급 — 사후에 그럴듯하게 꾸미지 않는다

과거 사건·숫자·외부 사실·도구 결과를 주장할 때 필요한 경우 다음 태그를 붙인다.

| 태그 | 뜻 |
|---|---|
| `[캡처]` | 동일 조건 screenshot/image 증거 |
| `[영상]` | motion/interaction 영상 |
| `[런타임]` | 실제 브라우저/앱 상태에서 관측 |
| `[테스트]` | Playwright/자동 테스트/검사 결과 |
| `[코드]` | 소스 구조·동작 확인 |
| `[커밋]` | Git diff/commit/PR 이력 |
| `[대화]` | 당시 사용자-AI 대화에 명시됨 |
| `[사용자평가]` | 사용자의 직접 관찰·판단 |
| `[플러그인]` | Product Design/Flourish/Figma 등 도구 산출물 |
| `[문헌]` | 외부 문헌·공식 가이드; 출처가 있어야 함 |
| `[추론]` | 위 근거로부터 현재 논리적으로 도출한 해석 |
| `[재구성]` | 당시 기록이 없어 사후에 복원한 판단 과정 |

`[추론]`과 `[재구성]`을 구분한다. **당시 무슨 생각을 했는가**는 대화/로그가 없으면 함부로 복원하지 않는다. 근거가 없으면 `기록 없음`이 허위보다 낫다.

모든 문장에 태그를 붙이지 않는다. "이 문장이 틀렸다면 무엇을 확인해야 하는가?"에 답할 수 있는 사실 주장에 붙인다.

### 대화 인용 규칙
- CASE에서 특정 사용자 문제 제기나 AI의 초기 framing이 **판단을 바꾼 전환점**이면, 현재 대화 원문 또는 export가 있을 때 1~3개의 짧은 핵심 발화를 그대로 인용한다.
- 인용은 장식이 아니라 `왜 판단이 바뀌었는가`를 복원하는 증거다. 긴 대화 전체를 복사하지 않는다.
- 현재 Chat에서 직접 확인한 원문은 `[대화]`로 표시할 수 있다. 별도 machine-export transcript가 없으면 그 사실을 CASE/부록에 명시한다.
- 기억 요약이나 사후 서술을 따옴표로 원문처럼 만들지 않는다. 이 경우 `[재구성]`을 쓰거나 `기록 없음`이라고 적는다.
- 대화량이 많거나 커리어/방법론 가치가 높으면 `CASE-nnn_TRANSCRIPT_EXCERPTS.md` 같은 부록을 두고 main CASE에서는 turning point만 요약·링크한다.

## 7. 기록 시점 트리거

| 순간 | 기록 |
|---|---|
| 이상한 화면/동작을 처음 본 순간 | F의 `발단` 후보를 먼저 적는다. 원인을 알기 전에 적어야 왜곡이 적다 |
| 중요한 후보를 고른 순간 | **구현 전에 D**. 선택지와 버린 이유를 같이 적는다 |
| 후보를 기각한 순간 | D의 `버린 것과 이유`에 즉시 남긴다. 결과물이 없어서 가장 잘 사라지는 기록이다 |
| AI/Plugin의 제안을 사람이 수정·반박한 순간 | R 후보. 다음 프로젝트에서도 쓸 재사용 규칙이 있는지 본다 |
| 사고가 해결된 순간 | O + 재발 방지책. 자동화 가능한지 판단한다 |
| 결론이 바뀐 순간 | 이전 항목을 삭제하지 말고 `철회/번복됨`과 새 ID를 연결한다 |
| 시스템/워크플로우 자체가 여러 사건을 거쳐 진화했을 때 | 아래의 **CASE 방법론 사례**를 작성한다 |

## 8. CASE — 운영 기록을 묶어 "왜 이런 시스템이 생겼는가"를 설명한다

F/D/O/R은 일상 운영 기록이다. 반면 커리어 포트폴리오, AI 사용 패턴 개선, 다른 프로젝트로의 이식뿐 아니라 **사용자 본인이 과거의 문제 정의·반론·판단 변화를 다시 확인하기 위해서도** 여러 기록을 묶은 방법론 사례 서사가 필요하다.

CASE는 새 운영 기록 종류가 아니다. `cases/CASE-nnn_*.md`에 두는 **합성·해설 계층**이다.

### CASE를 만들 조건
- 여러 번의 대화·수정·반론을 거쳐 하나의 workflow/설계 시스템이 생겼다.
- 사용자의 문제 정의 방식이나 AI 검증 방식 자체가 재사용 가치가 있다.
- "최종 결정"보다 그 결정이 나온 논의가 커리어/방법론적으로 의미 있다.
- 사용자가 명시적으로 사례 기록을 요청했다.

### 방법론 변경과 CASE 연결 의무

AI 역할, Plugin/Skill orchestration, source of truth, validation/handoff 구조, creative generation 방법론 또는 기록 방식이 바뀌면 **같은 작업 단위에서 CASE를 작성하거나 갱신**한다. 모든 D/R 항목에 `| CASE | ... |` 필드를 하나만 둔다. 과거 항목도 현재 연결을 보강하되 당시 본문을 바꾸지 않는다.

허용 값은 `CASE-001` 같은 실제 main CASE ID(여러 개는 쉼표로 구분), `불필요 — 구체적인 비방법론 사유`, 또는 `보류 — 구체적인 사유; 재검토: 재개 조건`이다. 빈 사유, `N/A`, `TODO`, 단순 `보류`, 없는 CASE나 transcript만 있는 번호는 허용하지 않는다. placeholder와 중복 필드도 실패한다. 이 사유는 사람의 판단 기록이며 checker가 방법론 여부를 이해한다는 뜻이 아니다. 사용자가 CASE 작성을 명시했다면 보류를 완료로 처리하지 않는다.

main CASE 번호는 유일해야 한다. 동일 번호의 transcript/영문 요약은 부록으로 허용한다. 새 ledger는 만들지 않는다. 중요한 대화의 원문이 handoff에만 있으면 **Chat이 옮긴 발췌의 재수록**임을 밝히고, AI 응답 요약은 직접 인용으로 위장하지 않는다.

### CASE 필수 구조
1. **배경** — 왜 이 문제가 생겼나
2. **논의 흐름** — 사용자 문제 제기 → AI 응답 → 반론/재검토 → 판단 변화. 사건 순서를 생략해 결론만 남기지 않는다.
3. **핵심 대화 근거/핵심 발화** — 비유·문제 정의·검증 요구처럼 맥락이 손상되면 안 되는 표현. 원문이 있으면 짧게 인용하고, 없으면 원문 부재를 명시한다.
4. **구축된 시스템/산출물** — 문서·코드·plugin routing·commit
5. **재사용 가능한 AI 사용 패턴** — 다른 프로젝트에 옮길 수 있는 요청/검증 방식
6. **AI가 기여한 것 / 사용자가 기여한 것** — 역할을 구분한다.
7. **한계와 반사실 부재** — 과장하지 않는다.
8. 필요 시 **대화 발췌 부록 / 영문 1-page summary**

### 인간 재열람 품질 기준
CASE를 다 읽은 사람이 다음 질문에 답할 수 있어야 한다.

1. 처음에는 무엇이 문제라고 생각했는가?
2. AI가 처음 어떤 해법 또는 framing을 제시했는가?
3. 사용자가 무엇을 반박·재정의했는가?
4. 어떤 증거/논리 때문에 판단이 바뀌었는가?
5. 최종적으로 어떤 문서·Skill·검사·코드가 생겼는가?
6. 사용자의 기여와 AI의 기여를 구분할 수 있는가?

이 질문이 답되지 않으면 문서 길이와 상관없이 CASE는 미완성이다.

CASE의 서사는 반드시 관련 F/D/O/R ID와 commit을 가리킨다. 대화 전문이 없으면 없는 부분을 꾸며내지 않는다. 원문 export가 있으면 부록을 분리하고 인용을 기계 대조하는 것이 최선이다.

## 9. 자동 검사 — 있는 기록뿐 아니라 가능한 범위에서 "없는 기록"과 "빈 서사"를 잡는다

`scripts/check-uiux-records.cjs`를 `npm test`에 포함한다.

현재 자동 검사 범위:
- F/D/O/R 항목의 필수 절과 ID 중복
- R의 `재사용 규칙`, D의 `되돌려야 하는 조건`
- 근거 태그 또는 명시적 `기록 없음`
- D/R의 CASE 필드 누락·중복, 빈/placeholder 사유, 보류 재검토 조건 및 유효한 main CASE 연결
- main CASE 번호 중복
- CASE가 관련 F/D/O/R을 실제로 참조하는지
- CASE가 배경/논의 흐름/구축 결과/재사용 패턴/한계를 포함하는지
- CASE가 실제 대화 증거를 쓰거나, 원문 부재를 `[재구성]`/`기록 없음`으로 명시하는지
- CASE가 사용자 기여와 AI 기여를 구분하는지
- `.claude/skills/*`가 provenance 문서에 등록되어 있는지
- UI/UX MASTER/Index가 기록 규약과 체크리스트를 가리키는지

자동 검사는 문장의 통찰 수준까지 판정하지 않는다. 그래서 `11_CHECKLISTS.md`의 인간용 CASE 체크를 함께 유지한다.

### 아직 자동으로 유도하지 못하는 것
현재 v2는 `main.tsx`에 여러 route/state가 모여 있고 design token/component registry가 완전히 정규화되어 있지 않다. 따라서 "새 top-level UI 갈림길이 생겼는데 D가 없다"를 코드만으로 안정적으로 추론하면 오탐이 크다.

**가짜 ledger를 하나 더 만들어 해결하지 않는다.** 다음 중 하나가 canonical source가 될 때 자동 누락 검사를 승급한다.
- component registry
- semantic design-token registry
- route/navigation registry
- feature flag registry
- 승인된 UI change ID의 구조화된 source

그 전까지 기각 후보와 새 갈림길은 `11_CHECKLISTS.md`의 사람 트리거가 차선의 그물이다.

## 10. 읽는 사람 기준

이 기록은 미래의 설계자만을 위한 복기 노트가 아니다.

- **현재/미래의 사용자 본인**: 왜 이 시스템을 만들었고 어떤 문제 제기·반론이 결정을 바꿨는지 다시 체감할 수 있어야 한다.
- **미래의 우리 팀**: 왜 이 구조가 생겼는지 다시 판단할 수 있어야 한다.
- **심사위원·제3자**: 배경지식이 없어도 결론의 흐름을 따라갈 수 있어야 한다.
- **커리어/포트폴리오 독자**: "AI를 썼다"가 아니라 **어떻게 문제를 정의하고, AI의 제안을 검증·반박·구조화했는지**가 보여야 한다.
- **다음 AI**: 같은 rejected idea와 같은 협업 실수를 반복하지 않아야 한다.

설명은 늘리되 주장의 강도는 늘리지 않는다. 기록이 없으면 `기록 없음`이라고 쓴다.
