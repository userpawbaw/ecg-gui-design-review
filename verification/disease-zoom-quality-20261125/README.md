# 질환 탭 축 확대 — 품질 · 방식 비교 (D-199 2차, 2026-11-25)

사용자: 「품질 면에서 떨어지지 않았을까 걱정되는데 모바일 환경이라 확인이 어려워서」 · 「보통 어떻게 처리하는거지? 외부 방식을 한번 조사해서 … 분석해봐」.

## 도구
- `zoom_quality.cjs` (`?zoomdbg`): 같은 확대 순간(보기 v, 진행 e = 0 · .25 · .5 · .75 · 1)을 정석(매 프레임 전부 그리기)과 빠른 길로 그려 PNG. `analyze.py`: 평균 차이 · PSNR · 크게 다른(>40/255) 화소 % · 선명도 비(밝기 기울기 에너지, 빠른/정석).
- `bench.cjs`: 같은 확대 40장을 방식별로, 래스터 포함(getImageData로 그리기 완료까지) / JS만.
- `fps_modes.cjs` · `fps_overlay.cjs` (`?zoomfps`): 실제 투어의 확대 fps.

## 성능 — 이 환경(headless, CPU 래스터)
- `bench.txt` · `bench_rampcache.txt`(래스터 포함, 감속 없음): 정석 8–11 ms · 나눔 7–9 ms · 통째 4.6–5.4 ms. 감속 4배: 정석 40–56 · 나눔 34–41 · 통째 22–26 ms.
- **정정**: 1차 보고의 「54–69 → 12–17 ms」는 JS 시간만 잰 값이었다(래스터 제외). 래스터까지 넣으면 통째 늘임이 정석의 약 2배, 나눔은 약 1.2배 빠르다.
- 실제 투어 fps(`fps_modes.txt`, 1920 × 1032): 감속 없음 정석 34–42 · 통째 48–56 · 나눔 47–59. 감속 4배는 모두 7–14 fps — 프로파일(`../disease-zoom-perf-20261125/split_in_profile.txt`)의 49 %가 JS 밖(이 환경의 소프트웨어 페이지 합성)이고 덧층 옵션을 꺼도 같다(`fps_overlay.txt`). 이 부분은 GPU가 있는 실제 노트북과 다르다 — 사용자 기기에서 `?zoomfps`로 확인.
- 함께 고친 것: 확대 중 한 프레임에 그리기 요청이 두 번 와서 두 번 그리던 것(같은 보기면 건너뜀), 매 프레임 `getBoundingClientRect`(강제 레이아웃, 프로파일 7 %) → ResizeObserver 값. 램프 캐시(`putImageData` 재생성 방지)는 이 환경에서 차이 없음 `[측정]` — GPU 캔버스에서의 이득은 `[추정]`.
