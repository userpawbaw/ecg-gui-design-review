# 경험 플레이북 — 설계 규칙 분석과 기본 틀 검토

작성 2026-10-09. 사용자 요청 `[대화]`:
- "어떤 작업을 진행하려고 하면 해결한 방법을 선택해라와 같은 식으로 각 케이스에 대해 먼저 권장 방안을 적은 문서를 만들어놓고"
- "별도 문서나 세부 항목으로 내 경험 … 권장 방식에 도달하게 된 과정까지 볼 수 있게 분리한다"
- "이 기록에는 여러 시행착오간의 연결성이 중요해."

이 문서는 세 가지를 담는다.
1. 조직과 전문가가 경험을 나중에 참고할 지식으로 바꾸는 방법론 조사(§1).
2. 그 조사에서 뽑은 설계 규칙(§2).
3. 사용자 기본 틀을 설계 규칙과 비교한 결과(§3).

실제 기록 형식과 검사기는 `01_FORMAT.md`에 있다.

## 1. 방법론 조사 — 무엇을 배웠나

| 방법론 | 핵심 구조 | 이 시스템에 주는 교훈 |
|---|---|---|
| **NASA Lessons Learned Information System(LLIS)** | 교훈마다 "계기가 된 사건(driving event)" 요약과 권고(recommendation)를 함께 둔다. 권고는 교육·모범 사례·규정으로 흘러간다 `[문헌]` | 사건과 권고를 한 단위로 묶는다 |
| **GAO-02-195, NASA OIG IG-12-012** | NASA 관리자 중 LLIS에 입력해 본 사람은 23 %뿐이었다. 이유는 "찾기 어렵고 쓸모 있는 교훈이 안 나옴", 시간 부족, 실수를 말하기 꺼림이었다. 10년 뒤 감사에서도 "프로젝트 관리자가 LLIS를 일상적으로 검색하지 않음"이었다 `[문헌]` | **쌓는 것보다 꺼내 쓰이는 것이 어렵다.** 작업 상황으로 찾게 하고, 작업 시작 지점에서 밀어 넣어야 한다 |
| **미 육군 CALL — 관찰·통찰·교훈(OIL), 사후 검토(AAR)** | 관찰 → 통찰 → 교훈 → 교리·훈련·장비 수정으로 이어지는 단계. 실무자들 사이에는 "배운 교훈은 없고 관찰된 교훈만 있다"는 말이 있고, 너무 일반적인 AAR은 쓸모없다는 비판이 있다 `[문헌]` | 교훈은 규칙·도구·검사로 **제도화돼야** 학습된 것이다. 일반론은 기록 가치가 없다 |
| **Fry, "Why Do Lessons Learned Often Fail?"** | 교훈이 기록돼도 조직이 바뀌지 않는 "관찰됐지만 학습되지 않음"이 실패의 표준 설명이다 `[문헌]` | 위와 같다 |
| **Architecture Decision Record(ADR, Nygard)** | 상태·맥락·결정·결과(단점 포함). 뒤집힌 결정은 지우지 않고 "대체됨"으로 두고 새 기록과 잇는다 `[문헌]` | 권장안이 바뀌어도 이전 권장안은 남기고 링크한다. 결과에는 단점도 쓴다 |
| **설계 근거(IBIS, QOC — Questions·Options·Criteria)** | 질문, 선택지, 기준, 선택지별 평가. 다만 풍부한 근거 체계는 유지 비용이 커서 잘 채택되지 않는다 `[문헌]` | 비교 단계에는 선택지와 기준을 남긴다. **필수 항목은 최소로** 둔다 |
| **패턴 언어(Alexander, 소프트웨어 패턴)** | 맥락 · 문제 · 힘(충돌하는 제약) · 해법 · 결과 맥락 · 알려진 사용처. 좋은 패턴은 풀지 못한 힘도 말한다. 한 패턴의 결과 맥락이 다음 패턴의 문제가 되는 **그물**이다 `[문헌]` | "언제 읽나"(맥락), "남은 한계"(풀지 못한 힘), 기록 사이의 연결(그물) |
| **Toyota 집합 기반 설계 — 상충 곡선·한계 곡선** | 과거 개발에서 "어디까지는 되고 어디부터는 안 되는지"를 곡선으로 저장해 다음 설계가 실패한 영역을 다시 탐색하지 않게 한다 `[문헌]` | **실패한 길과 그 경계도 지식**이다. "가지 말 길"과 "그 길이 될 수도 있는 조건"을 남긴다 |
| **Toyota 요코텐(횡전개)·A3 보고서** | 한 곳의 개선을 A3 한 장(문제 → 원인 → 대책 → 결과)으로 다른 현장에 옮긴다. 쌓는 책임자를 둔다 `[문헌]` | 한 장으로 읽히는 권장 카드 |
| **Klein, 핵심 결정 방법(Critical Decision Method)** | 전문가 인터뷰에서 결정 자체보다 **상황을 알아챈 단서(cue)**를 캐낸다. 전문가는 단서를 기억 속 원형과 맞춰 빠르게 판단한다 `[문헌]` | "이 길이 틀렸다는 신호"를 따로 기록한다. 같은 함정에 일찍 들어선 것을 알아채게 한다 |
| **Google SRE 무책 사후 분석(blameless postmortem)** | 사람이 아니라 기여 원인을 쓴다. 후속 조치에는 담당과 완료 기준을 둔다. 주인 없는 조치는 대표적 실패 유형이다 `[문헌]` | 사실 위주. 교훈마다 "어디에 강제됐는가"를 적는다 |
| **Diátaxis(문서 4분류)** | 작업 안내(how-to)와 설명(explanation)을 섞지 않는다. 설명이 작업 안내를 오염시키는 것이 가장 흔한 문제다 `[문헌]` | 권장 카드는 작업 안내, 여정은 설명. 사용자 기본 틀의 분리와 같다 |

## 2. 설계 규칙 DR-1 ~ DR-12

| ID | 규칙 | 근거 | 이 시스템에서 |
|---|---|---|---|
| DR-1 | **할 일과 이유를 다른 문서에 둔다.** 할 일 문서는 짧고 명령형, 이유 문서는 서사 | Diátaxis, ADR | 권장 카드 `P-*` / 여정 `J-*` |
| DR-2 | **사건이 아니라 작업 상황으로 찾게 한다.** 카드마다 "언제 읽나"를 두고, 작업 시작 시 그 목록을 먼저 보게 한다 | LLIS 미사용(GAO), 패턴의 맥락 | `언제 읽나` 필드, README 색인, AGENTS.md 작업 전 규칙 |
| DR-3 | **권장안에는 그 방법으로 실제 도달한 품질과 증거를 붙인다.** "이 방법이면 여기까지 간다"가 다음 작업의 출발 기준이다 | 패턴의 결과 맥락·알려진 사용처, 상충 곡선 | `도달 수준`(증거 경로 필수) |
| DR-4 | **실패한 길도 지식으로 남기고, 왜 실패했는지와 될 수도 있는 조건을 적는다** | 한계 곡선, ADR 기각, QOC | `가지 말 길` — 항목마다 여정 노드 인용 |
| DR-5 | **시행착오를 사슬로 잇는다.** 각 시도는 "무엇이 불만이어서 시작했나(계기)"와 "결과가 다음 시도를 어떻게 불렀나(다음)"를 가진다. 서로 다른 주제(머리 모양 → 리그)도 같은 사슬에 놓는다 | 패턴 언어 그물, IBIS 이력 | 여정 노드 `T1 … Tn`의 `계기`·`다음` |
| DR-6 | **틀린 길에 들어섰다는 신호를 남긴다** — 결론보다 먼저 보이는 증상 | Klein CDM 단서 | `틀린 길이라는 신호` |
| DR-7 | **타협한 지점과, 그 뒤 실제로 더 도달한 품질을 남긴다.** 다음 작업이 같은 곳에서 멈추지 않게 한다 | 사용자 요구(조기 타협 방지), 집합 기반 설계의 조기 수렴 경계 | 판정 `타협` + `타협하면 안 되는 지점` |
| DR-8 | **교훈은 어디에 강제됐는지 적는다**(검사기·skill·스크립트·체크리스트). 강제 장치가 없으면 이유를 적는다 | OIL "관찰 ≠ 학습", SRE 조치 담당 | `강제 장치` 필드 |
| DR-9 | **사실·근거 위주, 사람 탓 없이.** 사실 주장에는 근거 태그. 당시 기록이 없으면 `[재구성]` 또는 `기록 없음` | SRE 무책, 기존 `10_RECORD_KEEPING.md` §6 | 근거 태그 공용 |
| DR-10 | **뒤집힌 권장안은 지우지 않고 대체 표시 후 새 카드와 잇는다** | ADR 대체 | 상태 `대체됨 → P-nnn` |
| DR-11 | **필수 항목은 최소로, 선택 항목은 기록 내용이 요구할 때만 필수가 된다.** 빈칸을 채우게 만드는 양식은 억지 기록을 낳는다 | QOC 유지 비용·저채택, AAR 일반론 비판 | 조건부 필수(여정에 `기각`이 있으면 `가지 말 길` 필요 등)와 억지 기록 검사 |
| DR-12 | **운영 기록(F/D/O/R)을 복사하지 않고 링크한다.** 여정은 그것들을 시간순으로 꿰는 실 | 기존 기록 규약 | 노드 `기록` 필드는 실제 ID·경로만 |

## 3. 사용자 기본 틀 검토

사용자 틀: (가) 상황별 권장 방안 문서를 먼저 두고, (나) 별도 문서·세부 항목으로 경험(실패한 시도, 여러 방식 비교 후 선택 과정)을 분리해, (다) 도달 가능했던 목표 지점을 먼저 확인하고 이유까지 이해하게 한다. 그리고 (라) 시행착오 사이의 연결성.

| 사용자 틀 요소 | 대응 규칙 | 판정 | 보강 |
|---|---|---|---|
| (가) 권장 방안 먼저 | DR-1 | **유지** — 방법론과 일치 | 카드 이름을 작업 상황으로 짓는다("~할 때") — DR-2 |
| (나) 경험을 분리 | DR-1, DR-12 | **유지** | 경험 문서는 F/D/O/R과 겹치지 않게 "시도 사슬"로 쓰고 세부는 링크 |
| (다) 도달 가능했던 목표 지점 | DR-3 | **유지·강화** | 증거 경로가 없는 "도달 수준"은 검사기가 막는다 |
| (라) 연결성 | DR-5 | **유지·강화** | 노드마다 `계기`와 `다음`을 필수로. 주제가 달라도(표현 양식 → 메시 → 리그) 한 여정에 둔다 |
| 실패 기록 | DR-4 | 유지 | 실패마다 "될 수도 있는 조건"을 붙여 영구 금지가 아니라 경계로 남긴다 |
| — 없음 — | DR-2 | **추가** | 찾는 경로. 작업 시작 시 색인을 보는 규칙(AGENTS.md) |
| — 없음 — | DR-6 | **추가** | 틀린 길 신호 |
| — 없음 — | DR-7 | **추가** | 타협 지점(사용자 문제의식에는 있었으나 틀에는 칸이 없음) |
| — 없음 — | DR-8 | **추가** | 강제 장치 |
| — 없음 — | DR-10, DR-11 | **추가** | 대체 규칙, 조건부 필수와 억지 기록 검사 |

결론: 기본 틀의 두 층 구조는 그대로 쓴다. 다음 다섯 가지를 더한다.
1. 작업 상황 색인.
2. 틀린 길 신호.
3. 타협 지점.
4. 강제 장치.
5. 조건부 필수와 억지 기록 검사.

여정은 F/D/O/R 위에 놓이는 시간순 사슬로 정의한다. 그래서 새 운영 기록 종류가 아니라 **읽는 순서가 다른 두 층**(권장 → 여정 → 운영 기록)이 된다.

### 기존 CASE와의 차이
CASE(`docs/uiux_system/cases/`)는 "왜 이런 **작업 방식·시스템**이 생겼나"를 설명하는 방법론 사례다. 독자는 사람과 포트폴리오다. 플레이북은 "다음에 같은 **산출물**을 만들 때 무엇을 하라"이고, 독자는 다음 작업자(사람 또는 AI)다. 둘 다 F/D/O/R을 가리키지만 질문이 다르다. 사례 하나가 둘 다에 쓰일 수 있다. 예를 들어 이번 기록 체계 자체는 CASE-007, 사람 리그 경로는 J-001/P-001이다.
